# openmediad — план проекта

Свой медиа-движок для Яндекс Станции Мини 3 (bergamot): один Go-бинарник `openmediad`, который заменяет штатный
проигрыватель `maind --mediad`, играет из любых источников и выводит звук куда угодно. Собирается на компьютере с нужным
набором компонентов, заливается на колонку и ставится одной командой.

Это главный рабочий документ проекта. Он написан так, чтобы по нему мог работать и человек, и агент в новой сессии без
доступа к истории разговоров.

- Статусы задач: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено. «Проверено» значит: тесты зелёные, а если задача

## 2. Цель и принципы

**Цель.** Универсальный и простой медиа-движок для колонки: музыка, голос Алисы, звонки таймеров и будильников, позже Spotify,
SoundCloud, радио, приём по сети и с телефона; вывод на динамики, в Bluetooth-наушники, в сеть. Движок полностью заменяет
штатный `mediad`, остальная система (Алиса, дисплей, подсветка, кнопки) работает как раньше. Колонка слабая, поэтому движок
должен оставлять место чужим проектам; лишние компоненты убираются при сборке.

**Аудитория.** Владельцы колонок Яндекс с root-доступом (в основном Россия). Первая модель — Станция Мини 3 (bergamot,
прошивка `0.369.1.50.4794652521.20261021.117`); другие — позже, через профили устройств (фаза 13).

**Как этим пользуются:**

```sh
go run ./tools/build -without soundcloud            # на компьютере: собрать под колонку с нужными компонентами
go run ./tools/build -deploy 192.168.1.12          # или сразу собрать и залить в /tmp/openmediad/openmediad
ssh -p 2222 root@192.168.1.12 /tmp/openmediad/openmediad install   # на колонке: установить и включить автозапуск
openmediad config                                   # настройки
openmediad uninstall                                # колонка снова штатная
```

**Принципы (по убыванию важности):**

1. **Колонка не должна сломаться.** Любой сбой ведёт к штатному пути (`mediad`). Всё обратимо одной командой.
2. **Система не замечает подмены.** События плеера — байт в байт как у `mediad`, правила выведены из записей трафика и
   сверены с ними.
3. **Простота важнее оптимизации.** Понятный код и работающая функция сначала; ужимать — только то, что по замеру мешает (§13).
4. **Модульность.** Компонент выключается при сборке и в настройках, не затрагивая остальные.
5. **Измерять, а не гадать.** Каждая проверка «всё чисто» имеет положительный контроль: намеренная порча обязана её ронять.
6. **Звук штатного стека неприкосновенен.** `aplay` никогда не убивается `SIGKILL`; к общему смесителю подключается только
   32-битный клиент.

## 3. Что уже известно

### 3.1. Эксперименты (предыдущая версия `omd`)

Проект вырос из экспериментов: папка `openmediad/` в репозитории `Bergamoting` (там же разбор шины `quasar messaging/` и агент
подсветки `logo-led test/`). Код экспериментов переносится сюда по карте §19, их журнал замеров — в `docs/research/HISTORY.md`.

Что работало в экспериментах (проверено на колонке, 27.10.2026):

- **Шим** между `platformd` и `mediad`: правило `iptables` заворачивает соединения на `omd`, кадры идут 1:1 (1826 кадров
  сверено, расхождений 0, задержка ≈0,5 мс), откат за ≈1 с, страж снимает правило при гибели шима.
- **Музыка Яндекса** играет сам шим: HTTPS + AES-128-CTR + разбор MP4 + декодер GStreamer колонки, перемотка, зеркала,
  нормализация к −14 LUFS (подтверждена с точностью 0,02 дБ), приглушение во время диалога, возврат звука при паузе.
  События сверены побайтно (1796 событий, 0 расхождений). Пользователь слушал: разницы со штатной нет.
- **Голос Алисы**: Ogg/Opus на чистом Go (`go-opus`), длинные ответы цепочкой потоков, прерывание, события (2683 события, 0
  расхождений), запуск PCM за 28 мс против 62 мс у штатного пути.
- **Звонки таймеров и будильников**: файл раскодирован в память, играет по кругу до `release` (908 событий, 0 расхождений).
- **Спектр для дисплея и подсветки** в iohub — совпадение со штатным 0,02–0,05 дБ.
- **Откаты**: поток не открылся / нет звука 3 с → команда уходит `mediad`; при остановке шима плееры мягко передаются `mediad`
  (музыка продолжается с того же места).
- **Отладочный порт** 6701: живой журнал с пояснениями, SSE, pprof.

Чего не было: постоянной установки, файла настроек, Bluetooth-вывода, сетевого вывода, других источников, полной замены.

### 3.2. Колонка (выжимка)

| Тема | Что известно |
|---|---|
| Железо | 4 × Cortex-A53 ≈1,2 ГГц, 244 МБ ОЗУ (свободно ≈90–120 МБ); ядро 4.9 64-битное, userspace 32-битный (armhf) |
| Доступ | `ssh -p 2222 root@<ip>`, пароль пустой; `scp`/`sftp` нет — файлы через `ssh '… cat > файл' < файл`; `pgrep` нет (`ps \| grep` находит сам себя) |
| Файловые системы | rootfs — ubifs, смонтирован только для чтения (правка: `mount -o remount,rw /` → правка → `sync` → `mount -o remount,ro /`); `/data` — постоянный, всё своё в `/data/opt`; `/tmp` — tmpfs, **это ОЗУ** |
| Автозапуск | `S99quasar` → `onboot.sh` → `run.sh` → `quasar_launcher2 launch.json`; пользовательский хук `/etc/init.d/S99zdropbear` уже есть |
| Процессы | один бинарник `/system/vendor/quasar/maind` в ролях `--platformd` (Алиса, iohub, почти всё), `--mediad` (плеер), `--telemetry`, `--fluent-bitd`; `maind --gst-launch` — встроенный GStreamer; `maind --cli` — меню для проверок (текстовые вопросы Алисе, пауза) |
| Шина | TCP на 127.0.0.1; кадр `[u32 LE длина][protobuf-конверт {252: тело, 253: тип}]`; схем в прошивке нет, поля читаются по номерам |
| Порты | 9906 audioclient (плеер), 9900 mediad, 9875 aliced, 9903/9910 iohub, 9908 update_health_check; полный список — `docs/BUS-PROTOCOL.md` |
| Звук | ALSA `default` → `plug` → `dmix_speakers` (48 кГц, 2 канала, буфер 160 мс, период 20 мс) → `hw:0,0` (усилитель ACM8625); громкость — аппаратный `Master` 0–255, им управляет платформа; `libasound` 32-битная — свой вывод только через системный `/usr/bin/aplay` |
| GStreamer в `maind` | есть `fdsrc fdsink filesrc filesink decodebin qtdemux aacparse avdec_aac mpegaudioparse avdec_mp3 souphttpsrc queue typefind audioconvert audioresample`; нет `audiotestsrc`, `faad`, `mpg123audiodec`; на неверном конвейере **не завершается** — запускать только со сторожем по времени |
| Bluetooth | BlueZ 5.70, `bluealsa` 4.1.1 (`a2dp-sink`, `a2dp-source`, `hfp-ag`), кодек только SBC; звук с телефона играет `bluealsa-aplay -D bluetooth` (softvol) в общий смеситель, **мимо `mediad`** [проверено 28.10.2026, BUS-PROTOCOL.md §2.7]; PCM наушников — `plug:bluealsa:DEV=<MAC>,PROFILE=a2dp` **[вывод, с наушниками не проверено]** |
| Файлы прошивки | сертификаты `/system/vendor/quasar/ca-certificates.crt`; звуки `/system/vendor/quasar/sounds/…`; звонок таймера и будильника — `common/timer.wav` (по содержимому MP3 64 кбит/с, ≈9,27 с) |
| Нагрузка | `platformd` постоянно ест ≈1,3 ядра (слушает микрофоны); штатный `mediad` при музыке ≈17 % ядра и 21 МБ Pss, в простое ≈0 % и 10–16 МБ Pss |

## 4. Соглашения по коду

- **Имя.** Репозиторий, бинарник и модуль Go — `openmediad`. Путь модуля до публикации — просто `openmediad`; при публикации
  на GitHub можно заменить на полный (механическая замена импортов, §18).
- **Язык.** Имена пакетов, типов, функций и переменных — английские. Комментарии, сообщения об ошибках, журнал, вывод CLI,
  README и `docs/` — русские. Сообщения коммитов — русские.
- **Go.** Версия — из `go.mod`. `CGO_ENABLED=0`, статическая сборка; цель на колонке — `linux/arm64`. Всё, кроме системных
  вызовов колонки, собирается и тестируется на компьютере (Linux, Windows, macOS): платформенный код — в файлах `*_linux.go`
  с заглушками для остальных систем.
- **Зависимости.** Только из `vendor/` (сборка без сети). Каждая — в `THIRD_PARTY.md` (зачем, версия, лицензия), хэши файлов —
  в `vendor.sha256`. Новая зависимость — осознанное решение с записью в §18.
- **Размер.** Файл — одна ответственность, ориентир до 300 строк; больше 500 — разбить. Пакет — одна тема. Функция длиннее
  экрана — повод задуматься.
- **Компонент** — отдельная папка: `doc.go` (что делает пакет, что проверено), `register.go` (регистрация в реестре),
  `config.go` (секция настроек и умолчания), код, тесты.
- **Комментарии** объясняют «зачем», а не «что». Факт о колонке в комментарии — с пометкой достоверности и ссылкой на раздел
  `docs/`.
- **Ошибки** оборачиваются с контекстом: `fmt.Errorf("открытие потока: %w", err)`. `panic` — только для ошибок программиста.
- **Конкурентность.** Блокирующее (запуск процессов, сеть) — никогда в горутине, которая разбирает кадры шины. Не держать
  блокировку при вызове чужих функций (колбэков). Данные из буфера кадра копировать, если они нужны после возврата.
- **Время.** Код, зависящий от времени, получает часы снаружи (`Now`, `After`), чтобы тесты шли на виртуальном времени.
- **Секреты** не попадают никуда (журнал, отладочная страница, ошибки): ключ потока (поле 39), URL целиком (в нём подпись),
  JSON директив (поле 7), содержимое голосовых чанков.
- **Внешние процессы** — всегда с таймаутом и сторожем. `aplay` останавливается только закрытием stdin или `SIGINT`.
- **Никакой работы в `init()`**, кроме регистрации компонента. Компоненты создаются при первом использовании; выключенный
  компонент не запускает горутин и не выделяет память.

## 5. Архитектура

### 5.1. Общая схема

```
                     ┌──────────────────── openmediad run (демон) ────────────────────────────┐
 platformd ──9906───►│ quasar/shim (или quasar/server в режиме replace)                        │
     ▲               │        │ кадры                                                           │
     │ события 127   │        ▼                                                                 │
     └───────────────┤ quasar/mediad — эмуляция протокола mediad (автоматы плееров, события)   │
                     │        │ «открой, играй, пауза…»            ▲ «готов, играет, кончился»  │
                     │        ▼                                    │                            │
                     │ engine — потоки, классы (music/voice/alert), фокус и приглушение,       │
                     │          маршруты «класс → выходы», позиция по часам                    │
                     │   ▲ PCM                                       │ PCM                     │
                     │ source/*  yandex · tts · sounds · radio ·     sink/*  speaker ·         │──► динамики, наушники, сеть
                     │           spotify · soundcloud · netin · btin        bluetooth · netout │
                     │                                                                         │
                     │ spectrum ──► quasar/iohub ──► iohub (дисплей, подсветка)                │
                     │ quasar/aliced — фразы Алисы → команды своим источникам                  │
                     │ control — unix-сокет для команд CLI · debug — веб-порт 6701             │
                     └─────────────────────────────────────────────────────────────────────────┘
 guard.sh (busybox sh) — страж: запускает демон, держит правило iptables, при сбое возвращает штатный путь
```

Протокол Quasar — один из «пультов» ядра. Ядро не знает о шине; источники и выходы не знают ни о шине, ни друг о друге.

### 5.3. Правила зависимостей между пакетами

- `audio`, `quasar/pb`, `journal`, `buildinfo` — ни от чего своего не зависят.
- `codec/*` → `audio`. `source/*`, `sink/*` → `audio`, `codec/*`. Источники и выходы не импортируют друг друга, `engine`
  и `quasar`. Исключение — `bind.go` источников паритета (`yandex`, `tts`, `sounds`): переводчик «команда mediad → поток
  движка» импортирует `engine` и `quasar/mediad` и лежит рядом с источником, чтобы тот выключался одним тегом (§20).
- `engine` → `audio` и интерфейсы источников и выходов. О шине не знает.
- `quasar/*` → `engine` (через интерфейсы), `audio`, `spectrum`. Источник `yandex` создаётся эмуляцией mediad из команды
  `play`, но сам о шине не знает (получает `yandex.Track`).
- `app` — единственное место, где всё соединяется. `cli` → `control`, `config`, `system/*`, `app` (только для `run`).
- Компоненты попадают в бинарник только через `cmd/openmediad/with_*.go` (§6.2).

### 5.4. Ключевые интерфейсы (черновик, уточняется в фазе 2)

```go
// audio: формат PCM внутри движка — всегда S16LE.
type Format struct {
	Rate     int // Гц, обычно 48000
	Channels int // 1 или 2
}

// engine: класс потока определяет приоритет, приглушение и маршрут.
type Class int

const (
	Music Class = iota // музыка и прочие долгие потоки
	Voice              // голос Алисы
	Alert              // звонки таймеров и будильников, системные сигналы
)

// Source — откуда берётся звук.
type Source interface {
	Format() audio.Format
	Open(ctx context.Context) (Info, error) // сеть, декодер; Info.Duration = 0 — длительность неизвестна (поток)
	Read(p []byte) (int, error)             // PCM; блокируется, пока данных нет; io.EOF — конец
	Seek(pos time.Duration) error           // ErrNotSeekable у живых потоков
	Close() error
}

// Sink — куда выводить; Output — открытый вывод одного потока.
type Sink interface {
	Name() string
	Available() bool // например, наушники подключены
	Open(f audio.Format) (Output, error)
}

type Output interface {
	Write(p []byte) (int, error) // блокируется в темпе воспроизведения
	Delay() time.Duration        // сколько записанного ещё не прозвучало (оценка)
	Drain() error                // доиграть остаток и закрыть
	Abort()                      // оборвать сразу (у aplay — SIGINT, не SIGKILL)
}

// Stream — поток в движке: источник, класс, маршрут, состояние.
type Stream interface {
	ID() string
	Play()
	Pause() // вывод стоит, источник и позиция держатся; непрозвучавшее возвращается в буфер
	Seek(pos time.Duration)
	Close()
	Pos() time.Duration // по часам вывода, а не по записанным байтам
}

// Events — колбэки потока; вызываются без удерживаемых блокировок движка.
type Events struct {
	Ready   func(dur time.Duration) // открыт, первые ≈300 мс звука готовы
	Playing func()                  // первый звук ушёл в выход
	Ended   func()                  // доиграл до конца
	Failed  func(err error)         // не смог; до первого звука — повод для отката на mediad
}

// registry: компонент сборки.
type Component struct {
	Name    string     // «spotify»: так же называются секция [source.spotify] и тег сборки
	Kind    Kind       // Source, Sink, Service
	Summary string     // строка для --help
	Config  func() any // структура настроек с умолчаниями
	New     func(env Env, cfg any) (Module, error)
}

type Module interface {
	Start(ctx context.Context) error
	Stop()
}
```

### 5.5. Пример: как играет музыка Яндекса

1. `platformd` присылает `prefetch`/`play` → `shim.Intercept` → `mediad.Machine` (плеер вида audio).
2. Автомат создаёт поток `engine.Open(Music, yandex.New(track), events)` и выпускает `STARTING`, `PLAYING`, `progress`, `flag`
   с таймингами `mediad` (`docs/BUS-PROTOCOL.md`).
3. Поток читает PCM у источника в кольцо, применяет нормализацию трека и приглушение, пишет в выход по маршруту `music`,
   отдаёт звук спектру.
4. `Ready/Playing/Ended/Failed` → автомат → события типа 127 → всем соединениям платформы.
5. `Failed` до первого звука → автомат возвращает сохранённую команду настоящему `mediad` (откат).

### 5.6. Режимы интеграции

| | **shim** (по умолчанию) | **replace** (фаза 12) |
|---|---|---|
| Как встаём | правило `iptables` заворачивает соединения к 9906 на наш порт 19906; к `mediad` ходим с адреса 127.0.0.2 | `mediad` убран из `launch.json` (с бэкапом); слушаем 9906 и 9900 сами |
| Штатный `mediad` | работает всегда: горячий резерв, играет всё, что мы не умеем; стоит ≈10–16 МБ | не запущен; страж поднимает его при нашем сбое (холодный резерв, исследование R1) |
| Правка rootfs | только скрипт автозапуска | скрипт автозапуска и `launch.json` |
| Условие | — | закрыто всё из §10.4 |

### 5.7. Процессы на колонке

- `openmediad run` — демон (запускает страж).
- `guard.sh` — страж на busybox `sh`, отдельный от демона: если демон упал, правило `iptables` не должно остаться (иначе
  платформа не дойдёт до `mediad`, и Алиса замолчит).
- Дочерние процессы демона: `maind --gst-launch` (декодер, пока открыт трек), `aplay` (пока звучит), позже `librespot`.
- `openmediad <команда>` — короткоживущий CLI, говорит с демоном через `/tmp/openmediad/ctl.sock`.

### 6.2. Механизм

- Компонент регистрируется в `init()` своего `register.go`: `registry.Register(registry.Component{…})`. Регистрация ничего
  не запускает и не выделяет.
- Подключение к бинарнику — отдельный файл с тегом:

  ```go
  // cmd/openmediad/with_spotify.go
  //go:build omd_spotify

  package main

  import _ "openmediad/internal/source/spotify"
  ```

- Демон запускает компоненты из реестра, у которых в настройках `enabled = true`. Секция настроек для компонента, которого
  нет в сборке, — предупреждение, а не ошибка: один файл настроек годится для разных сборок.

### 6.3. Сборка

Основной способ — `go run ./tools/build` (работает на Windows, Linux и macOS; `make` и `sh` не нужны):

```
go run ./tools/build                           # под колонку (linux/arm64), компоненты по умолчанию → dist/openmediad
go run ./tools/build -with radio,spotify       # добавить опытные компоненты
go run ./tools/build -without debug,spectrum   # убрать стандартные
go run ./tools/build -host                     # под этот компьютер (для проверок)
go run ./tools/build -list                     # компоненты и их теги
go run ./tools/build -check                    # собрать три набора: по умолчанию, минимальный, максимальный
go run ./tools/build -deploy 192.168.1.12      # собрать и залить на колонку по ssh (порт 2222) в /tmp/openmediad/
go run ./tools/build -dev                      # собрать openmediad-dev
go run ./tools/build -verify                   # целостность vendor/: хэши файлов и go mod verify
```

`tools/build` вызывает `go build -trimpath -ldflags "-s -w -X openmediad/internal/buildinfo.Version=…" -tags …`; версия —
из `git describe`, если git есть, иначе `0.0.0-dev`. Ручной способ тоже работает:
`GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -tags omd_no_debug ./cmd/openmediad`.

| Команда | Что делает | Фаза |
|---|---|---|
| `openmediad`, `help [команда]`, `-h`, `--help` | помощь и сведения о сборке; без аргументов демон **не** запускается | 0 |
| `version`, `--version` | одна строка: версия, коммит, дата, цель | 0 |
| `components` | компоненты: в сборке / включены в настройках / работают сейчас | 3 |

| `test-sound [выход]` | тихий тестовый сигнал в выход | 5 |
| `reboot` | корректно остановить движок (плееры уходят `mediad`), `sync`, перезагрузка | 5 |
| `bt list \| scan \| pair \| connect \| disconnect \| forget \| use` | Bluetooth-наушники (D-Bus BlueZ; `use` — выбрать наушники для выхода `bluetooth`) | 6 (сделано) |
| `play URL`, `play -stop` | проверка своих источников без голосовых команд | 8 |

- Коды выхода: 0 — успех, 1 — ошибка, 2 — неверные аргументы, 3 — не та система (не колонка или неизвестная модель без

- Команды, меняющие систему, работают только на колонке и от root; на компьютере честно говорят «эта команда — для колонки».
- У всех команд, меняющих систему, есть `-dry-run` (показать план) и откат при ошибке на любом шаге.
- **`config` с редактором:** копия файла открывается в `$EDITOR`, иначе `nano`, иначе `vi` (есть ли `nano` на колонке —

  изменилось то, что на лету не применяется.
- **CLI ↔ демон:** unix-сокет `/tmp/openmediad/ctl.sock` (права 0600), строки JSON: `{"cmd":"status"}` →
  `{"ok":true,…}`. Без `net/http`.

## 8. Установка на колонку

### 8.1. Где что лежит

```
/data/opt/openmediad/
  bin/openmediad              бинарник
  guard.sh                    страж (пишет install из шаблона в бинарнике; обновляется вместе с ним)
  openmediad.conf             настройки
  backup/                     оригиналы изменённых файлов rootfs + manifest.json (пути, sha256, дата, версия)
  state/                      счётчик неудачных запусков, отметка установки, «автозапуск выключен»
  cache/                      раскодированные звуки и прочее, что можно пересоздать
  log/                        журнал в файл, если включён в настройках
/etc/init.d/S98openmediad     скрипт автозапуска
/usr/bin/openmediad           ссылка на бинарник (чтобы команда работала из любого каталога; §20)
/tmp/openmediad/              ctl.sock, pid, guard.log (маленькие файлы; /tmp — это ОЗУ)
```

### 8.2. `install`

1. Проверки (часть `doctor`): модель и прошивка, права root, `iptables -t nat` с `REDIRECT`, `/usr/bin/aplay`, `maind`,
   место на `/data`. Неизвестная модель — отказ без `-force`; неизвестная прошивка — предупреждение и только режим shim.
2. Если уже установлено — это обновление: остановить движок, настройки сохранить.
3. Создать `/data/opt/openmediad/…`, скопировать себя (`os.Executable`) через `.new` + переименование, записать `guard.sh`
   и настройки по умолчанию (если их нет).
4. Бэкап того, что будет изменено, с `sha256` в `backup/manifest.json`.
5. `mount -o remount,rw /` → записать `/etc/init.d/S98openmediad` → `sync` → `mount -o remount,ro /` → сверить
   записанное с ожидаемым.
6. Запустить (`start`, §8.5) и дождаться, что платформа подключилась через шим (4 соединения за ≤90 с).
7. Напечатать итог: что установлено, как смотреть состояние, как удалить.

Ошибка на любом шаге — откат уже сделанных шагов, колонка остаётся штатной.

### 8.3. `uninstall`

Остановить движок (правило снимается, плееры уходят `mediad`) → `remount rw` → удалить скрипт автозапуска, вернуть файлы
из бэкапа со сверкой `sha256` → `sync` → `remount ro` → удалить `/data/opt/openmediad` (настройки — только с `-purge`) →
дождаться, что платформа подключена к `mediad` напрямую (4 соединения). Итог проверки: файлы rootfs совпадают с бэкапом.

### 8.4. Автозапуск и страж

Скрипт автозапуска минимален, вся логика — в `guard.sh` на `/data` (его можно обновлять без правки rootfs):

```sh
#!/bin/sh
# S98openmediad — автозапуск openmediad (ставит openmediad install, убирает openmediad uninstall).
# Нет файлов на /data — ничего не делаем: колонка работает штатно.
D=/data/opt/openmediad
[ -x "$D/bin/openmediad" ] && [ -f "$D/guard.sh" ] || exit 0
case "$1" in
	start|"") sh "$D/guard.sh" boot >/dev/null 2>&1 </dev/null & ;;
	stop) sh "$D/guard.sh" stop ;;
esac
```

Страж (`guard.sh boot|start|stop`):

- **boot:** если автозапуск выключен или счётчик неудачных запусков ≥ `fallback.max_crashes` — ничего не запускать
  (штатный путь), записать причину. Иначе добавить правило `iptables` (shim) и запустить `openmediad run`. Скрипт стоит
  раньше `S99quasar`, поэтому правило появляется до того, как платформа подключится к плееру; перезапускать `mediad` не нужно.
  Демон открывает свой порт, только когда настоящий `mediad` начал принимать соединения (как в экспериментах).
- **Слежение (раз в секунду):** демон умер → сразу снять правило (платформа переподключится к `mediad` напрямую за ≈1 с);
  прожил меньше 60 с → счётчик +1; перезапуск с паузой 2, 4, 8… с; счётчик дошёл до предела — сдаться до перезагрузки или
  ручного `openmediad start`. Демон проработал 10 минут — счётчик в 0.
- **stop:** снять правило → `SIGTERM` демону (он отправляет платформе `PAUSED` для играющей музыки и отдаёт звонки `mediad`
  по ещё открытым соединениям) → ждать до 15 с.
- Правило `iptables` ставит и снимает **только страж**; демон его не трогает (один владелец — меньше путаницы).
- Журнал стража — `/tmp/openmediad/guard.log`, не больше 64 КБ.

### 8.5. Ручные `start` и `stop`

`start`, когда платформа уже подключена к `mediad` напрямую: запустить страж → правило → перезапустить `mediad` штатным
лаунчером (`SIGTERM`, лаунчер поднимает его за <1 с; цена — теряется плеер на паузе) → дождаться 4 соединений через шим, иначе
откат. `stop`: страж снимает правило и останавливает демон → дождаться 4 прямых соединений. Это перенос `shim-on.sh` и
`shim-off.sh` из экспериментов.

### 8.6. Обновление прошивки (OTA)

Обновление может заменить rootfs и стереть скрипт автозапуска; тогда колонка просто работает штатно (это безопасно).
`doctor` и `status` замечают «установлено, но автозапуска нет» и предлагают `install` заново. Новая прошивка может изменить
протокол: незнакомая версия прошивки — предупреждение в журнале и `doctor`.

### 8.7. `doctor`

Модель и прошивка; бинарник и страж на месте; скрипт автозапуска на месте и совпадает с ожидаемым; правило `iptables` есть
тогда и только тогда, когда демон работает; демон отвечает по сокету; настройки корректны; `aplay`, `maind`, `iptables nat`
доступны; места на `/data` и `MemAvailable` достаточно; порты 19906 и 6701 свободны или заняты нами; есть ли редактор
для `config`; счётчик неудачных запусков.

## 9. Настройки

- **Файл:** `/data/opt/openmediad/openmediad.conf`. Нет файла — действуют умолчания. `install` пишет файл со всеми ключами
  и комментариями (шаблон хранится в бинарнике; `config reset` восстанавливает его).
- **Формат:** подмножество TOML — секции `[source.yandex]`, `ключ = значение`, строки в кавычках, числа, `true`/`false`,
  длительности строкой (`"300ms"`), списки `["a", "b"]`, комментарии после `#`. Парсер свой (≈200–300 строк, ошибки с
  номером строки), без зависимостей. Синтаксис совместим с TOML: при необходимости парсер заменяется библиотекой без правки
  файлов.
- **Проверка:** неизвестный ключ — ошибка (ловит опечатки); секция компонента, которого нет в сборке, — предупреждение.
- **Применение:** уровень журнала, маршруты, приглушение — на лету; остальное — при перезапуске демона (`config` предложит).

Пример файла по умолчанию (к фазе 3):

```toml
# Настройки openmediad. Правка с проверкой: openmediad config. Только проверка: openmediad config check.
# Строки — в кавычках, списки — в квадратных скобках, комментарии — после #.

[general]
mode = "shim"            # shim — штатный mediad работает рядом и подхватывает всё, что мы не умеем
                         # replace — только openmediad (появится в фазе 12)
log_level = "info"       # trace | info | warn | error
log_entries = 2000       # сколько записей журнала держать в памяти
log_file = ""            # файл журнала на /data; пусто — только в памяти (флеш не изнашивается)

[fallback]               # штатный mediad всегда рядом и подхватывает всё несыгранное (выключателя нет, §20)
max_crashes = 3          # после стольких падений подряд движок не запускается до перезагрузки

[debug]
enabled = true
listen = "0.0.0.0:6701"  # страница журнала для компьютеров домашней сети (только чтение)
cors = false             # true — разрешить читать журнал странице с другого адреса (локальный html-файл)

[route]                  # куда идёт звук каждого класса: первый доступный выход из списка
music = ["speaker"]      # например ["bluetooth", "speaker"]: наушники, а если их нет — динамики
voice = ["speaker"]
alert = ["speaker"]

[focus]
duck_gain = 0.25         # громкость музыки, пока Алиса слушает или говорит

[spectrum]
enabled = true
delay = "300ms"          # через сколько после передачи в aplay звук слышен: метка кадра спектра = расчёт + delay

[source.yandex]
enabled = true

[source.tts]
enabled = true

[source.sounds]
enabled = true
preload = ["common/timer.wav", "common/spotter_start.mp3", "common/spotter_cancel.mp3", "common/volume_sound.mp3", "common/bluetooth_turning_on_jingle.opus", "common/bluetooth_turning_off_jingle.opus"]   # раскодировать заранее: звук начнётся без задержки

[sink.speaker]
device = "default"
aplay = "/usr/bin/aplay"
```

## 10. Интеграция с Quasar

Справочник по сообщениям — `docs/BUS-PROTOCOL.md` (переносится из экспериментов в фазе 0), разбор всей шины —
`docs/research/QUASAR-PROTOCOL.md`.

### 10.1. Протокол

`quasar/pb` (protobuf без схем, разбор без выделения памяти), `quasar/wire` (кадры, конверт, типы, сборщики `CancelDialog`,
`PausePlayback`), `quasar/msg` (окна `AudioCommand`, `AudioEvent`, `AliceState`, `Remoting`, `Handshake`) переносятся почти
без изменений, вместе с тестами.

### 10.2. Эмуляция `mediad`

- Три вида плееров: **audio** (вид 1, музыка), **voice** (вид 2, голос Алисы), **file** (вид 4, звонки). У каждого — свой файл
  с автоматом; общий жизненный цикл (таймеры плеера, откат с пересылкой сохранённых команд, позиция последнего `progress`,
  мягкая передача при остановке) — в отдельном файле, без дублирования.
- Сборка событий: `event.go` (музыка) и `plain_event.go` (голос и файлы) — перенос как есть; это ядро совместимости,
  сверенное побайтно.
- Тайминги, правила полей и переходы состояний — в `docs/BUS-PROTOCOL.md`; в коде — константы со ссылкой на раздел.
- Решения автомата пишутся в журнал с пояснением простыми словами; тексты пояснений живут рядом с кодом решения.
- Важные находки, которые нельзя потерять: повторный `prefetch` того же плеера не сбрасывает его состояние; плеер, не
  заигравший за 15 с, отдаётся `mediad`; `STARTING` всегда раньше `PLAYING`, даже если звук пошёл раньше таймера; на паузе
  держится один плеер не дольше 30 минут; позиция — по часам, а не по записанным в `aplay` байтам.

### 10.3. Режим shim

Перенос `internal/shim` экспериментов: кадры 1:1, `Intercept` (решает автомат), `Broadcast` (наши события всем соединениям
платформы), `ForwardTo` (возврат команды `mediad`), закрытие слушателя, пока `mediad` недоступен (иначе лавина
переподключений платформы). Сводка по кадрам и сверка шима переезжают в `devtools`.

### 10.4. Режим replace — что нужно закрыть (фаза 12)

- [ ] слушать 9906 (audioclient) и 9900 (`mediad`; кто и зачем подключается — R3);
- [ ] при подключении клиента присылать то же, что `mediad` (наблюдался `Remoting ClockStorage`, метод 31 — R4);
- [ ] отвечать `update_health_check` (тип 250 `{1:"mediad"}`, порт 9908 — R2);
- [ ] эквалайзер (поле 35 команды): принять, по возможности применить (R5);
- [x] Bluetooth-плеер «телефон → колонка» (R6): **не нужен** — его играет `bluealsa-aplay` без `mediad` (проверено 28.10.2026, BUS-PROTOCOL.md §2.7);
  от движка нужны только сигналы включения и выключения Bluetooth (плеер файлов, сделано);
- [ ] радио и потоки без ключа — сейчас их играет `mediad`; в replace — источник `radio` (фаза 8);
- [ ] события вида 5 (diag) — нужны ли кому-то (R16);
- [ ] незнакомые команды — запись `warn` в журнал и разумный ответ;
- [ ] холодный резерв: как страж запускает `maind --mediad` сам (R1);
- [ ] правка `launch.json` с бэкапом и сверкой; проверка, что платформа без `mediad` не ругается и не перезагружается (R2).
- Мультирум и стереопара — вне плана (не поддерживаются, это документируется).

### 10.5. Спектр для iohub

Перенос `spectrum` и `iohub`: окно Хэмминга, один БПФ на 40 мс по первым 1024 отсчётам, 513 полос, порог −80 дБ; вход —
после нормализации и приглушения; у голоса — моно-PCM декодера вместе с отсчётами pre-skip. Клиент iohub подключается при
первой отправке, вычитывает всё, что присылает сервер, закрывается после 5 минут простоя.

**Метка времени кадра** (поле 1) — момент, когда звук прозвучит: кадр уходит сразу, с меткой «время расчёта + `spectrum.delay`»
(по умолчанию 300 мс — запас трубы и смесителя после передачи в `aplay`); остановка потока (`6:2`) — через тот же `delay`,
когда последний кадр прозвучал. Так делает штатный mediad (приход − метка ≈ −0,29 с); кадры с меткой в прошлом платформа
не рисует — в экспериментах из-за этого не было анимации (docs/research/HISTORY.md, §22). `delay` подбирается глазами.

### 10.6. Диалог Алисы и голосовые команды (фаза 8)

- Наблюдатель `aliced` (только чтение) — для журнала и для команд своим источникам.
- Окончательная фраза: `AliceState.FinalPhrase()` (≈1 с до ответа Алисы). Нормализовать префикс «Алиса» и с запятой, и без
  неё (в режиме «слушать дальше» он приходит без запятой).
- Своя команда («включи … в спотифай», «пауза», «дальше», когда играет свой источник) → `wire.CancelDialog()` (Алиса не
  отвечает своё) → действие источника. Правила разбора — в настройках, а не в коде.
- Арбитраж с музыкой Яндекса: когда начинает играть свой источник класса music, музыку платформы ставим на паузу её же
  способом (`wire.PausePlayback`, **[вывод]**: проверить, что платформа присылает `pause` и считает музыку на паузе).

## 11. Звук: ядро, источники, выходы

### 11.1. Внутренний формат

PCM S16LE, 48 кГц (частота смесителя колонки), 1 или 2 канала. Источники с другой частотой (Spotify — 44,1 кГц) проходят
через ресемплер в `audio` (качество выбирается настройкой; на первое время допустим и `plug` ALSA внутри `aplay`).

### 11.2. Классы и фокус

- Классы: `music`, `voice`, `alert`. Одновременно играет один поток `music`; `voice` и `alert` звучат поверх.
- Пока у диалога фокус (команда `focus` 39:1 в shim; для своих источников — также `AliceState` LISTENING/BUSY/SPEAKING),
  `music` приглушается до `focus.duck_gain` плавно; после — плавно возвращается.
- Нарастание 150 мс при старте вывода (без щелчка). Затухание перед паузой и в конце — желательно, не обязательно
  (сейчас пауза обрывает `aplay`, возможен щелчок).

### 11.3. Маршруты

Настройка `[route]`: для каждого класса — список выходов по приоритету, берётся первый доступный. Выход пропал на ходу
(наушники отключились) — поток переезжает на следующий в списке. Возможность «зеркала» (звук одновременно в динамики и
в сеть) — в фазе 7.

### 11.4. Громкость

- Динамики: аппаратный `Master` (им управляют кнопки и платформа); движок его не трогает. Нормализация трека и приглушение —
  программные, внутри движка.
- Bluetooth и сеть: `Master` на них не действует. Движок читает `Master` и применяет такую же громкость программно
  (чтение — через ioctl управляющего устройства ALSA с подпиской на события, запасной путь — `amixer`; R14).

## 12. Журнал и отладка

- **Журнал** (`journal`): кольцо в памяти (`general.log_entries`, по умолчанию 2000), записи — время, уровень, источник,
  сообщение, пояснение простыми словами, данные без секретов. Пишут все компоненты через общий интерфейс. `openmediad logs`
  читает его через сокет. Запись в файл — по настройке и с пределом размера (флеш изнашивается, по умолчанию выключено).
  Ничего не пишется без предела в `/tmp` (это ОЗУ).
- **Отладочный порт** (компонент `debug`): по умолчанию включён, `0.0.0.0:6701`, только чтение: `/` — страница с живым
  журналом и состоянием, `/api/log` (`?since=`, `?format=ndjson`), `/api/stream` (SSE), `/api/state`. Открыт для компьютеров
  домашней сети (§18, Р6). На странице видны распознанные фразы и названия треков, но не ключи и не ссылки. pprof — только
  в сборке с `omd_pprof`.
- **`openmediad-dev`** — отдельный бинарник для разработчика: `observe` (клиент-наблюдатель шины), `pcap` (разбор записи
  `tcpdump -i lo`, `-voice-dir` для голоса), `timeline` (сжатая шкала команд и событий), `shimcheck` (сверка сторон шима),
  `pcmwatch` (смены состояния PCM и `trigger_time`), `voice-play` (замер задержки), `sanitize` (обезличивание записей, §15).
  На колонку ставится по необходимости в `/tmp`.

## 13. Бюджет ресурсов

Колонка: ≈90–120 МБ свободной памяти, 4 ядра ≈1,2 ГГц. Движок должен оставлять место чужим проектам, но **первые версии
не ужимаются**: сначала работающий и понятный код, потом замер на колонке, потом оптимизация того, что реально мешает.

### 13.1. Ориентиры (не жёсткие пределы)

| Состояние | Память своих процессов (Pss: демон + декодеры + `aplay` + …) | Процессор |
|---|---|---|
| Простой | до 15 МБ | ≈0 % (никаких опросов в простое) |
| Играет музыка Яндекса | до 45 МБ (в экспериментах ≈25 МБ, с предзагрузкой и паузой — до ≈50) | до 30 % одного ядра (эксперименты и штатный путь — ≈17 %) |
| Отвечает Алиса | +5 МБ к текущему | — |

Штатный `mediad` в режиме shim в эти цифры не входит: это цена режима (≈10–16 МБ).

### 13.2. Когда браться за оптимизацию

- `MemAvailable` на колонке опускается ниже 40 МБ в обычном сценарии;
- ориентир превышен больше чем в полтора раза;
- слышны провалы звука, или ответ Алисы заметно запаздывает против штатного;
- пользователь сказал, что мешает.

### 13.3. Правила для агентов

- **Не оптимизировать без замера на колонке**, который показывает проблему по §13.2. Замер — `openmediad status`
  (Pss своих процессов: сумма по `/proc/PID/smaps`, в ядре 4.9 нет `smaps_rollup`) и `top`.
- Не делать отдельную работу ради экономии меньше 1 МБ или 1 % ядра.
- Приёмы из запаса — по одному, с замером до и после; результат — в `docs/research/HISTORY.md`.
- Оптимизация, которая заметно усложняет код, — только с согласия пользователя.

### 13.4. Гигиена (ничего не стоит, соблюдать сразу)

- никакой работы в `init()`; компоненты создаются при первом использовании;
- внешние процессы живут, пока нужны: `aplay` — пока звучит, декодер — пока трек открыт;
- на паузе держится один плеер и не дольше 30 минут (как у `mediad`);
- журналы — в памяти с пределом, в `/tmp` ничего не растёт без предела;
- бинарник **не сжимать UPX**: 8 МБ разделяемых страниц файла превратятся в 8 МБ личной памяти процесса;
- прогрев (сертификаты, раскодирование звонка) — вне горячего пути, чтобы не задерживать кадры шины.

## 14. Безопасность и обратимость

1. `aplay` — **никогда** `SIGKILL`: оборванный посреди записи клиент может испортить общий смеситель, и замолчит вся колонка
   вместе с Алисой. Остановка — закрытием stdin (доиграет) или `SIGINT` (оборвёт). Не завершился — оставить и сообщить.
2. К смесителю `dmix` подключается только 32-битный клиент (системный `aplay`): состояние смесителя лежит в общей памяти
   с типами, размер которых зависит от разрядности **[вывод; проверять не будем]**.
3. rootfs меняют только `install`/`uninstall`: бэкап с `sha256`, `remount rw` на время одной правки, сразу `sync` и
   `remount ro`, сверка записанного.
4. Никогда не трогать boot, bootloader, recovery, разделы MTD. Не сбрасывать колонку. Не ставить обновления вручную.
5. Каждая команда, меняющая систему, имеет `-dry-run` и откатывается при ошибке на любом шаге.
6. Страж независим от демона: демон мёртв → правило снято за ≤2 с, платформа говорит с `mediad` напрямую.
7. Не принимать соединения, пока `mediad` недоступен (иначе лавина переподключений платформы и тысячи предупреждений
   в её журнале).
8. Перехватчик кадров не блокирует: обработка быстрая, всё долгое — в отдельных горутинах.
9. Буфер кадра принадлежит шиму и переиспользуется: что нужно позже — копировать.
10. `maind --gst-launch` — всегда со сторожем по времени (на неверном конвейере он не завершается); ему `SIGKILL` допустим
    после `SIGTERM` (смеситель он не держит).
11. Секреты — никуда (§4).
12. Отладочный порт только читает: никакого управления колонкой через него.
13. Проверки на колонке — тихо: громкость зажимается скриптом `scripts/dev/volume-clamp.sh` (платформа сама поднимает
    громкость звонка и будильника). В сценариях **не использовать** «удали все будильники» — удалит и настоящие.

## 15. Тестирование

- **Модульные тесты** идут на компьютере без колонки. Подделки: `aplay` → запись в память, GStreamer → поддельный декодер,
  часы → виртуальные, сеть → `httptest`.
- **Золотые тесты** сверяют наши события и кадры спектра с записями живого трафика. Записи с колонки (`pcap`) содержат
  идентификаторы аккаунта, подписанные URL и ключи, поэтому в репозиторий как есть не кладутся: тесты ищут их в каталоге
  `OMD_CAPTURES` и без него пропускаются. Задача фазы 1 — `openmediad-dev sanitize`: замена идентификаторов, URL и ключей
  строками той же длины (кадры остаются корректными), после чего часть записей ложится в `testdata/`.
- **Положительный контроль обязателен:** каждая проверка «нет расхождений» должна падать при намеренной порче правила.
- **Перед каждым коммитом:** `go vet ./...`, `go test ./...`, `go run ./tools/build -check`. В отчёте о проверке указывать
  число выполненных тестов, а не только «ok» (`-run` с опечаткой молча ничего не проверяет).
- **Проверка на колонке** — по чек-листу фазы; результат с датой — в `docs/research/HISTORY.md`.
- **Длинный прогон** (≥2 ч музыки с паузами, ответами Алисы и звонком таймера) — перед тем как что-то становится включённым
  по умолчанию.

Уроки экспериментов:

- дважды проверка «всё чисто» оказывалась пустой (сравнение с той же константой, что в коде; совпадение по пустому
  префиксу) — отсюда правило положительного контроля;
- ошибка «второй трек завис без звука» (повторный `prefetch`) нашлась только длинным прогоном;
- ленивая инициализация в горячем пути задержала кадр шины на 83 мс (чтение сертификатов) — прогревать заранее;
- кэш паузы без предела держал по декодеру (≈12 МБ) на каждую паузу;
- относительные пути и `grep` в проверочных скриптах прятали ошибки; `ps | grep` находит сам себя;
- громкость `Master` меняет не только пользователь: платформа (звонки, `smart_volume`).

## 20. Отклонения от плана в М1

Что при написании М1 сделано не так, как описано выше, и почему. Разделы выше поправлены там, где расхождение сбивало бы
с толку; остальное — здесь.

| Что | Как сделано | Почему |
|---|---|---|
| Привязки источников (§5.3) | `source/{yandex,tts,sounds}/bind.go` реализуют бэкенды автомата `quasar/mediad`; `source.go` о шине не знает | переводчик живёт рядом с источником: тег сборки убирает и то и другое |
| `codec/mp4` | отдельный пакет (+ `mp4test` — синтез файлов для тестов) | таблицы MP4 пригодятся не только Яндексу |
| `audio.Output` (§5.4) | без `Delay()`: позицию считает движок по часам (время записи минус `PosLatency`) | так было в экспериментах и проверено на колонке |
| Компонент `spectrum` | `quasar/iohub/register.go`; спектр считает движок, компонент только отправляет кадры | спектр — часть цикла вывода, iohub — только адресат |
| Новые пакеты `quasar/explain`, `quasar/observe`, `quasar/capture` | пояснения для журнала, наблюдатель шины, разбор записей | демон и `openmediad-dev` пользуются одним кодом |
| `quasar/aliced` (§5.2) | пока нет: наблюдение за диалогом для журнала — `app` через `quasar/observe` | разбор фраз в команды — фаза 8 |
| Новые пакеты `system/proc`, `system/layout`, `system/disk` | процессы и память (`status`, `doctor`), пути установки, место и режим монтирования | нужны `status`, `doctor`, `install` |
| `[fallback] enabled` (§9) | убран; добавлен `general.log_file_max_kb` | в shim штатный mediad подхватывает несыгранное всегда — выключатель ничего бы не делал; вернётся в фазе 12 (холодный резерв) |
| rootfs (§8.1) | кроме скрипта автозапуска — ссылка `/usr/bin/openmediad` (в манифесте; чужой файл не трогается) | PATH колонки не включает `/data`: без ссылки `openmediad config` не работал бы |
| Проба без установки | бинарник заливается в `/tmp/openmediad/openmediad`, а не в файл `/tmp/openmediad` | `/tmp/openmediad` — рабочий каталог демона |
| Скрытая команда `reroute` | страж вызывает её после падения демона и при загрузке: ждёт платформу через шим, при нужде один раз перезапускает mediad | иначе после перезапуска демона платформа осталась бы у mediad напрямую |
| Страж: код выхода 0 | демон, вышедший сам с кодом 0, считается остановленным (правило снято, страж выходит); падение — код ≠ 0 | так выглядят `kill` и выключение системы |
| Страж: `nice` | `nice -n -10` только если `nice` работает | в некоторых сборках busybox нет этого апплета |
| `OPENMEDIAD_ROOT` | префикс путей колонки для симулятора `scripts/dev/simulate.py`; на колонке не задаётся | проверка `start`/`install`/стража на компьютере |
| `scripts/shim-on.sh`, `shim-off.sh`, `shim-guard.sh` (§19) | не перенесены | их заменили `openmediad start`/`stop` и `guard.sh` |
| Справка | `openmediad --help` сгруппирован по назначению | команд стало 17 |
| Bluetooth-выход (фаза 6) до проверки с наушниками | код, тесты и проверки на колонке без наушников; компонент опытный (`-with bluetooth`) | пользователь проверит, когда будут наушники (R8) |
| Одноразовые системные звуки (фаза 8) | сделаны 28.10.2026 вместе с правками событий плеера файлов (общий uuid после STARTING, событие diag, средний битрейт по Xing) | без них в replace некому было бы играть звук после «Алиса» и щелчок громкости; данные из записей уже были |
