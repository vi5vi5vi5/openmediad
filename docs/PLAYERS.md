# Как написать плеер для движка

**Плеер движка** — компонент, который играет музыку сам: через движок (`engine`), а не через штатный `mediad` платформы. Сейчас такой один —
`spotify-soloist`; следующим может стать любой источник (радио, свой сервер, другой клиент Spotify). Платформа про такой плеер не знает: её кнопки, жесты
и голос управляют только её собственной музыкой (Яндекс.Музыкой). Чтобы пауза, «дальше» и «назад» работали и у вашего плеера, их принимает ядро
([core/control](../internal/core/control/README.md)) и раздаёт плеерам. **Вам не нужно ничего знать про кнопки, наушники, голос и Яндекс**: плеер говорит
ядру три вещи и выполняет команды.

## Что ядро делает за вас

Один раз, одинаково для любого плеера:

* принимает команду из любого источника: кнопка Алисы и жесты на колонке, кнопки Bluetooth-наушников, голос («Алиса, пауза»), короткие команды без «Алиса»,
  директивы облака, команды платформы;
* решает, **чей звук**: играет ваш плеер — команда ваша; играет Яндекс — не ваша; ничего не играет, а вы на паузе — «продолжи» и «дальше» достаются тому,
  кто играл последним;
* отсекает **повторы**: одно нажатие на колонке видно дважды (лог платформы и её команда), облако дублирует перехваченную фразу директивой;
* готовит автомат к **запуску очереди Яндекса**, который платформа затевает в ответ на жест, «играй» и «дальше»;
* **уступает звук**: заиграл ваш плеер — Яндекс на паузе, заиграл Яндекс — вы на паузе; запоминает, кто играл последним;
* объявляет **события** (пауза, продолжение, перемотка) даже когда они случились без ядра — например, в приложении вашего источника: подсветка рисует
  по ним штатные анимации прошивки;
* пишет в журнал, что и откуда выполнено.

Всё это проверено таблицей сценариев (`core/control/matrix_test.go`: обстановка × команда × источник): правила записаны в одном месте.

## Что нужно написать

Три метода (интерфейс `control.Player`) и, если нужно, четвёртый:

```go
// Accepts: слушаетесь ли вы этого источника. Обычно это настройки компонента: «голос включён», «кнопки включены».
func (c *Component) Accepts(o control.Origin) bool {
	switch o {
	case control.Voice, control.FastVoice, control.Cloud:
		return c.config().Voice
	case control.Speaker, control.Headphones:
		return c.config().Buttons
	case control.Virtual:
		return c.config().VirtualPlayer
	case control.Arbiter:
		return true // уступка звука не отключается
	}
	return false
}

// State: что с вами сейчас. Быстро, без ожидания сети: вас спрашивают каждые 100 мс.
func (c *Component) State() control.State {
	return control.State{
		Ready:     c.connected && c.loggedIn,      // можно выполнять команды
		Playing:   c.sounding || c.status == "playing", // играет или вот-вот заиграет
		Sounding:  c.sounding,                     // звук течёт в движок прямо сейчас
		Paused:    c.status == "paused",           // на паузе
		Resumable: c.status == "paused" && c.ours, // на паузе, и «продолжи» должно поднять именно вас
		Track:     c.trackID,                      // меняется вместе с треком
		NearEnd:   c.leftMS < 4000,                // трек доигрывается
	}
}

// Do: выполнить Pause, Resume, Next или Prev. Не ждать результата. Не вышло (нет связи) — вернуть ошибку.
func (c *Component) Do(cmd control.Cmd, from control.Origin) error {
	switch cmd {
	case control.Pause:
		return c.send("pause")
	// … Resume, Next, Prev; на всё остальное (Toggle тоже) — ошибка
	}
	return fmt.Errorf("команда %q не передаётся", cmd)
}
```

Необязательно: `Yielded()` (интерфейс `control.Yielder`) — ядро сообщает, что звук уступали из-за вас или вам: удобно для счётчика в `status`.

### Поля State

| Поле | Когда истина | Зачем ядру |
|---|---|---|
| `Ready` | есть связь и вход, команды выполнимы | неготовый плеер не получает команд |
| `Playing` | музыка идёт или вот-вот пойдёт | чья команда «пауза», кто хозяин звука |
| `Sounding` | звук действительно течёт в движок | уступка звука не должна срабатывать раньше звука |
| `Paused` | статус «на паузе» (чья бы ни была сессия) | пауза и продолжение, замеченные само: анимации |
| `Resumable` | на паузе и сессия ваша | «продолжи» и «дальше» достаются вам, если Яндекс не играл позже |
| `Track` | любая строка, меняющаяся с треком | перемотка в приложении: анимация «дальше» и «назад» |
| `NearEnd` | трек доигрывается (несколько секунд) | смена трека после него — обычный ход музыки, не перемотка |

Нет трека или вы не умеете сказать «на паузе с моей сессией» — оставьте поле пустым; ядро справится: без `Resumable` вам просто не достанется «продолжи» после
паузы, без `Track` не будет анимаций перемотки.

### Правила для Do

* **Не блокируйте.** Команда уходит и забывается; состояние придёт отдельно.
* **Ошибка означает «не выполнено».** Тогда ядро скажет источнику «не взято», и фраза уйдёт Алисе, а кнопка наушников — платформе: пусть ответит она, чем
  тишина.
* **Toggle не приходит**: ядро само сводит его к паузе или продолжению. Незнакомую команду отвергайте ошибкой.
* От `from` зависит только то, что вы решите учесть в статистике или в отмене диалога Алисы (Spotify отменяет диалог, когда выполнил голосовую фразу, чтобы
  облако не отвечало «не поняла»); решать «выполнять или нет» по источнику не нужно, это уже решило ядро.

## Как подключить

1. Пакет `internal/components/<имя>/` с `register.go`: `registry.Register(registry.Component{Name, Defaults, Template, New})`. Структура настроек с тегами
   `conf:"…"`, шаблон файла настроек с комментариями. Образец — `led-ring` (маленький) и `spotify-soloist` (полный плеер).
2. Паспорт в `internal/components/catalog/catalog.go`, файл `internal/components/included/include_<имя>.go` с тегом сборки; `go run ./tools/build -sync-docs`.
   Подробности — в [ARCHITECTURE.md](ARCHITECTURE.md), раздел «Компоненты».
3. Демон сам видит, что объект умеет `Accepts/State/Do`, и добавляет его к плеерам ядра (`attach` в `core/daemon/components.go`). Больше ничего регистрировать
   не нужно.
4. Звук отдавайте в движок потоком класса «музыка» (как делает `spotify-soloist`, `pcm.go`): тогда подсветка, громкость, наушники и спектр работают сами.
5. Подсветка источника: `led.Indicator` из службы `"led"` (`On(led.Source, Name, цвет)` при начале музыки и `Off` при остановке).

Службы ядра для компонента берутся из `env`: `registry.Use[*control.Hub](env, "control")` (если плееру нужно знать, хозяин ли он звука, для действий не про
воспроизведение — лайк, «включи музыку»: `hub.Owns(Name)` и `hub.Idle()`), `"led"`, `"engine"`, `"machine"`, `"swallow-voice"`.

## Как проверить

В `core/control/controltest` лежит всё готовое:

```go
func TestMyPlayerFollowsTheContract(t *testing.T) {
	c := newTestComponent(t)               // подключён к подделкам, а не к настоящему источнику
	controltest.CheckPlayer(t, c)          // договор: Accepts, State, Do не ломают ядро
}
```

* `controltest.CheckPlayer` проверяет договор: `Accepts` одинаково отвечает на любой источник и не паникует; `State` быстрый, безопасен при параллельных вызовах
  и не противоречит себе (звучит — значит, играет; играет и на паузе вместе не бывает); `Do` отвергает `Toggle` и незнакомые команды и не зависает.
* Чтобы проверить свой плеер вместе с ядром, соберите `control.Hub{Platform: &controltest.Platform{}}`, добавьте плеер (`hub.Add(Name, c)`) и вызывайте
  `hub.Do(control.Pause, control.Headphones)`; в `spotify-soloist/voice_test.go` так устроен стенд (`say`, `directive`, `setOwner`).
* Для проверки того, как ваш плеер видит остальной мир, есть `controltest.Player` и `controltest.Platform` (Яндекс играет, сколько раз готовили очередь
  Яндекса).
* Правила ядра («чей звук», повторы, очередь Яндекса, события) вам тестировать не нужно: они уже проверены таблицей сценариев. Если ядро ведёт себя не так, как
  нужно вашему плееру, правьте правило там (и строку таблицы), а не обходите в плеере.

## Чего плееру делать не надо

* Не слушать кнопки, наушники, голос и лог платформы самому: этим занимаются источники, а команду вам приносит ядро.
* Не решать, играет ли Яндекс, и не ставить Яндекс на паузу: это уступка звука, её ведёт ядро.
* Не готовить автомат к запуску очереди Яндекса после команд из `Do`: ядро делает это по источнику (кроме собственных сценариев вашего плеера вроде «включи
  <название>»: они вне управления воспроизведением, их готовит сам плеер, как `request.go` у Spotify).
* Не рисовать анимации паузы и перемотки: они приходят от событий ядра.

## Чего ядро пока не умеет

* Показывать плеер движка платформе как свой для дисплея и спектра — это отдельная возможность (`mediad.Machine.SetVirtual`), сейчас её использует Spotify
  (`virtual.go`); новому плееру она нужна, если на дисплее должны быть название и спектр.
* Выбирать между двумя плеерами движка, играющими одновременно: побеждает тот, кто заиграл позже, остальные ставятся на паузу.
* Анимации на часах (сегменты индикатора): формат файлов прошивки ещё не разобран.
