# Архитектура openmediad

Как устроен код: из каких частей состоит демон, кто кого вызывает и где что искать. Почему решения такие —
в [PLAN.md](../PLAN.md) (§5, §18), протокол шины — в [BUS-PROTOCOL.md](BUS-PROTOCOL.md), история экспериментов —
в [research/HISTORY.md](research/HISTORY.md).

## 1. Одной картинкой

```
                 ┌──────────────────────────── openmediad run ────────────────────────────────┐
 platformd ─9906─┼─► iptables REDIRECT ─► quasar/shim (127.0.0.1:19906) ──── как есть ────────┼─► штатный mediad (9906)
     ▲           │                           │ команды плееру (тип 8)            (с 127.0.0.2) │      (горячий резерв)
     │           │                           ▼                                                 │
     │ события   │   quasar/mediad.Machine — автоматы плееров audio / voice / file, как mediad │
     └───127─────┼──  │  «открой, играй, пауза, чанк голоса, звонок»   ▲ «готов, играет, конец» │
                 │    ▼                                                │                        │
                 │   привязки источников (bind.go): yandex · tts · sounds                       │
                 │    │  engine.NewStream(источник, класс, события)    │                        │
                 │    ▼                                                │                        │
                 │   engine — поток: источник → громкость класса → вывод; позиция по часам      │
                 │    │ PCM             │ кадры спектра                                         │
                 │    ▼                 ▼                                                       │
                 │   app.router ──► sink/speaker ──► sink/alsa (/usr/bin/aplay) ──► динамики   │
                 │                 quasar/iohub ──► iohub (дисплей, подсветка)                  │
                 │                                                                              │
                 │   journal (кольцо в памяти) ◄── все;  control (ctl.sock) ◄── CLI;  debug :6701 │
                 └──────────────────────────────────────────────────────────────────────────────┘
 guard.sh — страж: ставит и снимает правило iptables, запускает демон, считает падения (фаза 4)
```

Что openmediad не берёт себе (команды, которых он не понимает, выключенные компоненты, ошибки до первого звука),
проходит к штатному `mediad` без изменений. Поэтому любая часть движка может отказаться от работы, и колонка продолжит
играть штатно.

| `cmd/openmediad-dev` | инструменты разработчика: `observe`, `pcap`, `timeline`, `shimcheck`, `pcmwatch`, `sanitize`, `voice-play`, `play-yandex` | `devtools`, `quasar/*`, источники |

| `internal/source/*` | `yandex`, `tts`, `sounds`: источник (`source.go`) + привязка к эмуляции mediad (`bind.go`) + `register.go` | `engine`, `codec`, `quasar/mediad` (только привязки) |
| `internal/sink/*` | `alsa` (системный `aplay`), `speaker` (динамики) | `audio` |

| `internal/quasar/shim` | посредник перед настоящим mediad: перехват кадров, рассылка событий | `wire` |
| `internal/quasar/iohub` | сообщения спектра и клиент iohub; компонент `spectrum` | `engine`, `spectrum`, `journal` |
| `internal/quasar/explain` | пояснения простыми словами для журнала (что значит кадр и что сделал движок) | `msg`, `journal` |
| `internal/quasar/observe, capture` | клиент-наблюдатель шины; разбор записей pcap и своего формата | `wire`, `msg` |
| `internal/system/*` | `layout` (пути установки), `initd` (шаблоны стража и автозапуска), `install` (установка с бэкапом), `stock` (штатный mediad, соединения платформы), `iptables`, `device` (модель, прошивка), `proc`, `disk`, `clock`, `alsactl` | — |
| `internal/devtools` | код инструментов `openmediad-dev` | `quasar/*` |
| `tools/build` | `go run ./tools/build` — сборка с выбором компонентов, проверка наборов, заливка на колонку | `registry` |

Правила зависимостей:

- источники и выходы не импортируют друг друга и не знают о шине; исключение — `bind.go` источников паритета: это
  переводчик «команда mediad → поток движка», и он лежит рядом с источником, чтобы источник выключался одним тегом;
- `engine` не знает о шине и о конкретных источниках и выходах — только интерфейсы (`engine.Source`, `engine.Router`,
  `audio.Output`);
- `app` — единственное место, где всё соединяется. Компоненты подключаются к демону по интерфейсам, которые реализуют
  (см. §4), а не по именам.

## 3. Демон: запуск и остановка

`openmediad run` → `app.Run`:

1. Настройки (`config.LoadFile`; нет файла — умолчания). Режим `replace` пока отвергается.
2. Журнал: кольцо на `general.log_entries` записей, копия в терминал при ручном запуске, файл — если задан `log_file`.
3. Движок и маршрутизатор: `app.router` выбирает для класса потока первый доступный выход из `[route]`.
4. Автомат `mediad.Machine` и шим `shim.Proxy`. Пока ни один компонент не подключён, автомат прозрачен (`NoMusic`,
   нет `Voice` и `File`): всё играет штатный mediad.
5. Сокет команд `ctl.sock`. Если он уже занят живым демоном, второй демон выходит, ничего не тронув.
6. Компоненты сборки, включённые в настройках (§4). Модули (отладочный порт, спектр) запускаются последними.
7. Шим ждёт, пока настоящий mediad начнёт принимать соединения, и только тогда открывает свой порт.

`SIGTERM`/`SIGINT`: `Machine.Handoff` — играющая музыка встаёт на паузу с текущей позицией (платформа узнаёт об этом
по ещё открытым соединениям), звонок отдаётся mediad; через 150 мс шим закрывается, компоненты останавливаются в обратном
порядке. `SIGHUP` — перечитать настройки (как `openmediad config`).

На ходу применяются уровень журнала, маршруты и приглушение (`reload`). Режим, размер журнала, выход `speaker` и
включение компонентов — после перезапуска; ответ `reload` перечисляет, что ждёт перезапуска.

## 4. Компоненты

Компонент — пакет с `register.go`, который в `init()` вызывает `registry.Register` (и больше ничего не делает при
запуске). В бинарник пакет попадает через `cmd/openmediad/with_<имя>.go` с тегом сборки:

- компонент «по умолчанию» входит в сборку, пока не задан тег `omd_no_<имя>`;
- опытный — только с тегом `omd_<имя>`.

Каталог всех компонентов (и запланированных) — `internal/registry/catalog.go`. Тест в `cmd/openmediad` проверяет, что
файлы `with_*.go` и их теги совпадают с каталогом.

`registry.Component`:

- `Defaults` — указатель на структуру настроек с умолчаниями (`config.Toggle` даёт ключ `enabled`, остальные ключи —
  тегами `conf:"…"`); секция берётся из каталога;
- `Template` — кусок файла настроек по умолчанию с комментариями;
- `New(env, cfg)` — создать объект. Сервисы демона берутся из `env` по имени: `registry.Use[*engine.Engine](env, "engine")`
  (ещё `machine`, `journal`, `state`).

Демон подключает созданный объект по интерфейсам (`internal/app/components.go`):

| Объект реализует | Что делает демон |
|---|---|
| `mediad.Backend` | музыка: автомат отдаёт объекту команды плеера `audio` |
| `mediad.VoiceBackend` | голос Алисы |
| `mediad.FileBackend` (+ `Accepts(path)`) | звонки таймеров и будильников (только принятые файлы и только «по кругу до release», поле 1.50 = 0) |
| `Start(ctx) error` + `Stop()` | модуль: запускается после всех, останавливается при выходе |
| `Shutdown()` | вызывается при выходе (закрыть потоки, дождаться `aplay`) |
| `DebugState() any` | данные для `status -v` и отладочной страницы |

Ошибка `New` или `Start` одного компонента не роняет демон: он работает без него, и то, что делал компонент, остаётся
штатному mediad.

**Новый компонент:** запись в каталоге → пакет с `register.go` → `with_<имя>.go` → секция в шаблоне → тесты. Подробно —
PLAN.md, §6.

## 5. Как играет музыка Яндекса

1. Платформа шлёт `AudioCommand` (тип 8) на 9906; правило iptables приводит соединение в шим.
2. `app.intercept` разворачивает кадр и отдаёт команду `Machine.Handle`. Если автомат взял её себе, кадр к mediad
   не идёт, а в журнал пишется «перехвачено» с пояснением.
3. Автомат плеера `audio` вызывает `Backend.Open(id, Track, offset)` — это `source/yandex/bind.go`: он создаёт
   `yandex.Source` (HTTPS, расшифровка, таблицы MP4) и поток движка класса `music`.
4. Поток открывает источник в фоне (`Events.Ready`), по команде `play` открывает вывод через маршрутизатор
   (`sink/speaker` → `aplay`) и пишет PCM в темпе воспроизведения. Первый звук — `Events.Playing`.
5. Привязка переводит события потока в вызовы автомата (`Opened`, `Failed`, `Finished`), автомат собирает события mediad
   (тип 127) байт в байт и рассылает их всем соединениям платформы (`Proxy.Broadcast`).
6. Позиция для событий — по часам вывода с поправкой на задержку, а не по записанным байтам.
7. Пауза: вывод обрывается (`aplay` получает `SIGINT`, не `SIGKILL`), непрозвучавший звук возвращается в кольцо
   источника (`Rewinder`), продолжение начинается ровно с того места, которое было слышно.
8. Ошибка до первого звука (`Events.Failed`) — автомат возвращает команду штатному mediad (`Forward`), и трек играет он.

Голос (`tts`) и звонки (`sounds`) устроены так же: свой автомат в `quasar/mediad` (`voice.go`, `file.go`), своя
привязка в `bind.go` источника. Плеер файлов берёт только звонки: поле 1.50 стартовой команды = 0 (`msg.AudioCommand.FileLoops`),
звук идёт по кругу до `release`. Одноразовые системные звуки (1.50 = 1: звук после «Алиса», щелчок громкости) кончаются сами,
`release` к ним не приходит — их играет штатный mediad (иначе они зациклились бы; docs/research/HISTORY.md, §21).

**Спектр для дисплея.** Движок считает кадр спектра по тому, что ушло в вывод, и отдаёт его `quasar/iohub.Sender`. Тот
отправляет кадр сразу, с меткой «время расчёта + `spectrum.delay`» — когда звук прозвучит (как штатный mediad), а остановку
потока — через тот же `delay`. Кадр с меткой в прошлом платформа не рисует (HISTORY.md, §22).

## 6. Настройки

`/data/opt/openmediad/openmediad.conf` (другой — `OPENMEDIAD_CONFIG`). Формат — подмножество TOML, парсер свой
(`config/parse.go`), ошибки с номером строки. Ядро: `[general]`, `[fallback]`, `[route]`, `[focus]`, `[sink.speaker]`;
остальные секции принадлежат компонентам. Неизвестный ключ — ошибка; секция компонента, не вошедшего в сборку, —
предупреждение. Файл по умолчанию собирается из шаблона ядра и шаблонов компонентов сборки (`config.Template`).

`config.Set` меняет одно значение в тексте файла, сохраняя комментарии и порядок, и проверяет результат целиком. Запись —
атомарная (`.new` + переименование).

## 7. Журнал, команды, отладка

- **Журнал** (`journal.Journal`): каждая запись — время, уровень (`trace`, `info`, `warn`, `error`), источник (`shim`,
  `player`, `music`, `voice`, `sound`, `engine`, `aliced`, `system`), короткое сообщение, пояснение простыми словами
  и данные без секретов. Кадры шины пишутся на уровне `trace`; копии одной рассылки событий (по одной на соединение)
  в журнал попадают один раз.
- **Сокет** `/tmp/openmediad/ctl.sock` (другой каталог — `OPENMEDIAD_RUN`): запрос — строка JSON
  `{"cmd":"status"|"logs"|"follow"|"reload", …}`, ответ — строки `{"ok":true,"data":…}`. Права — только root.
- **Отладочный порт** (компонент `debug`, по умолчанию `0.0.0.0:6701`, только чтение): страница с живым журналом
  и состоянием; `/api/log?since=N`, `/api/stream` (SSE), `/api/state`. При включённом `debug` демон ещё наблюдает
  за диалогом Алисы (aliced, порт 9875) и пишет в журнал распознанные фразы.

## 8. Правила, которые нельзя нарушать

- Звук на динамики — только через системный 32-битный `/usr/bin/aplay` (общий смеситель `dmix` в общей памяти).
- `aplay` никогда не получает `SIGKILL`: остановка — закрытием stdin или `SIGINT`.
- `maind --gst-launch` — всегда со сторожем по времени; ему `SIGKILL` после `SIGTERM` допустим.
- Перехватчик кадров не блокирует: всё долгое — в отдельных горутинах. Буфер кадра принадлежит шиму: что нужно позже —
  копировать.
- Правило iptables ставит и снимает только страж; демон его не трогает.
- Секреты (подписанные URL, ключи, идентификаторы аккаунта) не попадают ни в журнал, ни в отладочный порт.

## 9. Страж, включение, установка

- **Страж** — `internal/system/initd/guard.sh`, встроен в бинарник и пишется на колонку командами `start` и `install`.
  Работает на busybox `sh` отдельно от демона: запускает `openmediad run`, ставит правило iptables и ждёт демон
  (`wait`). Демон завершился — правило снимается сразу; упал (код ≠ 0) — перезапуск через 2, 4, 8… с; быстрых падений
  (жил < 60 с) подряд `fallback.max_crashes` — страж сдаётся до перезагрузки или `openmediad start`. Состояние —
  `/tmp/openmediad/guard.state`, журнал — `guard.log`. Правило ставит и снимает только страж.
- **`start`** (`internal/cli/start.go`): пишет стража, запускает его отдельно от терминала, ждёт ответа демона по сокету,
  затем `stock.Rerouter`: если платформа подключена к mediad напрямую, mediad перезапускается (лаунчер Quasar поднимает
  его сам), и команда ждёт 4 соединения через шим. Не вышло — `guard.sh stop`, колонка штатная.
- **`install`** (`internal/system/install`): `/data/opt/openmediad` (бинарник, страж, настройки), манифест бэкапа,
  затем rootfs в одной правке (remount rw → скрипт автозапуска и ссылка → sync → remount ro). Каждый шаг кладёт в стек
  свой откат; ошибка — откат в обратном порядке. `uninstall` возвращает rootfs по манифесту и сверяет sha256.
- Соединения платформы считаются по `/proc/net/tcp` (`stock.ReadConns`): «через шим» — принятые на порту 19906, «напрямую» —
  клиенты порта 9906 минус они (сокет клиента, завёрнутый правилом, по-прежнему видит адресом 9906).
- **Симулятор** `scripts/dev/simulate.py` проверяет всё это на компьютере: поддельные mediad с лаунчером, platformd,
  aliced и iptables, корень колонки — каталог из `OPENMEDIAD_ROOT`.

## 10. Тесты

`go test ./...` идёт на компьютере без колонки: `aplay` подменяется записью в память, GStreamer — поддельным декодером,
сеть — `httptest`, часы — виртуальными. Демон целиком проверяется в `internal/app/app_test.go` с поддельным mediad.
Золотые тесты сверяют события с записями живого трафика: записи ищутся в `OMD_CAPTURES` и в `testdata/*.omdf`
(обезличенные `openmediad-dev sanitize`), без записей тесты пропускаются.
