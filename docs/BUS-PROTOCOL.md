# Шина плеера: справочник по сообщениям

Справочник по тому, что нужно шиму: команды плееру, события плеера, спектр для iohub. Все поля восстановлены по записям живого
трафика (схем в прошивке нет, `maind` собран в lite-режиме). Пометка **[проверено]** — подтверждено автоматической сверкой с записями,
**[вывод]** — выведено по поведению, **[догадка]** — смысл не подтверждён. Общая карта шины — [research/QUASAR-PROTOCOL.md](research/QUASAR-PROTOCOL.md).

## 1. Кадры и конверт

- Кадр: `[u32 LE длина][сообщение]`, лимит прошивки на размер кадра — 10 МиБ (`wire.MaxFrame`). **[проверено]**
- Сообщение — конверт protobuf: поле **252** = payload (bytes), поле **253** = тип (varint). **[проверено]** Бывают дополнительные поля (у metricad).
- Типы, нужные плееру: **8** команда плееру (platformd → mediad), **127** событие плеера (mediad → все клиенты), **85** `IOHubMessage`
  (iohub), **88** ответ iohub, **183** служебное iohub, **3** `AliceState` (aliced), **210** `Remoting` (вызовы методов Алисы).

## 2. Сервис плеера (`mediad`, порт 9906)

Платформа держит четыре постоянных соединения. Команды идут по одному, события `mediad` рассылает всем четырём
(одно и то же сообщение, байт в байт). **[проверено]**

### 2.1. Команда плееру (тип 8)

| Поле | Смысл |
|---|---|
| 1 | дескриптор трека (см. 2.2) — у `prefetch` и `play` |
| 22 | плеер: `{1: вид (1 audio, 2 voice), 2: uuid плеера, 3: id трека (у голоса пусто), 4: 0}` |
| 4 | пустое — `pause` (причина «completeDirective: PAUSE branch») |
| 29 | кадры Ogg/Opus голоса Алисы (`voice-chunk`); 30 — конец данных (`voice-eos`); 31 — `release` плеера |
| 50 | `crossfade`: `{1: мс, 2: мс, 3: мс}` (причина «updateCrossfade: wasStarted»), приходит сразу после старта трека |
| 35 | настройка эквалайзера (причина «onEqualizerConfig»), к конкретному плееру не привязана |
| 39 | `focus`: 1 — диалог занял аудиофокус, 0 — отдал |
| 13 | перемотка (причина «AUDIO_REWIND directive»): `{1: 0, 2: double секунд (относительно), 3: {…}}` |
| 40 | строка-ссылка (идёт в поле 8 событий) |
| 52 | причина (строка, отладочная): `prefetchDirective: for prefetch`, `AUDIO_PLAY directive`, `cancelDirective: …` и т. п. |

Назначение команды `Classify` определяет так (**[вывод]**, порядок важен): 29 → voice-chunk, 30 → voice-eos, 31 → release, 4 → pause,
50 → crossfade, 35 → equalizer; при наличии дескриптора — voice-start (плеер voice), prefetch (причина содержит «prefetch»), play; 39 → focus.

Последовательности **[проверено по записям]**:
- «включи музыку»: `focus 1` → голос Алисы (`voice-*`) → `prefetch` (id P) → ≈1 с → `release` голоса → `play` (тот же P) → `focus 0` → `crossfade`.
- «следующий трек»: `pause`(P1) и через ≈5 мс `play`(P2, новый трек).
- «пауза»: `pause`(P). «Продолжи»: `play` нового плеера P' того же трека с `offset_ms` = позиция паузы.
- перемотка: `other`(REWIND) на плеере P; штатный путь потом присылает `pause`(P) + `play`(P'', offset); у шима платформа этого не делала.
- ответ Алисы поверх музыки: `focus 1` → `voice-start/chunk/eos` → `release` голоса → `focus 0`.

### 2.2. Дескриптор трека (поле 1 команды)

| Поле | Смысл |
|---|---|
| 1 | id трека (строка) |
| 2 | URL потока (подписанный, `…/aac192-mp4`); содержит подпись доступа — в журналы не писать |
| 3 | `offset_ms` — с какого места играть (у возобновления и перемотки) |
| 4, 11, 18, 19, 34, 41, 43, 44, 48 | числовые признаки **[догадка]** (18 в событиях убирается) |
| 7 | JSON директивы (≈8 КБ): колбэки, идентификаторы запросов аккаунта — в журналы не писать |
| 8 | `{1: id запроса, 2: «music» либо «tts_play_placeholder», 3: id}` |
| 9 | метаданные: `{1: название, 2: исполнитель, 3: обложка, 4: контекст «Моя волна»…}` |
| 20 | «Track» |
| **21** | нормализация: `{1: истинный пик, дБ (double), 2: громкость трека, LUFS (double)}`; поправка = −14 − `2` **[проверено измерением, 0,02 дБ]** |
| 26, 27 | служебные (26 — пустая строка, 27 — число); в событии остаётся одно из них, см. 3.2 |
| 35 | фейды/кроссфейд: `{2: {3: мс, 4: мс}, 3: {1: мс, 2: мс}}` **[догадка по смыслу]** |
| 38 | время формирования, epoch мс |
| **39** | **ключ расшифровки потока: hex, 16 байт** — в журналы не писать |
| 42 | зеркала URL (повторяющееся поле, обычно 3) |
| 45 | битрейт, кбит/с (192) |
| 46 | мс, около длительности трека **[догадка]** |

### 2.3. Поток Яндекса

MP4 (`ftyp`, `uuid`, `moov` ≈39 КБ, `mdat`), AAC-LC 44,1 кГц стерео, `moov` в начале, сэмплы не фрагментированы (`stsz/stco/stsc/stts`).
Шифрование **AES-128-CTR**: ключ — поле 39, начальный вектор нулевой, счётчик = номер 16-байтного блока от начала файла
(поэтому подходит Range с любого смещения: счётчик = `offset/16`, первые `offset%16` байт гаммы пропускаются). HTTP отдаёт `206` на Range.
Длительность — `mvhd` (совпадает с прогрессом GStreamer, например 220288 мс). **[проверено]**

### 2.4. Событие плеера (тип 127)

Верхний уровень (порядок полей по возрастанию номеров) **[проверено побайтно]**:

| Поле | Смысл |
|---|---|
| 1 | вид: 1 смена состояния, 2 прогресс (≈1,06 с), 5 диагностика (шим не синтезирует), 6 flag |
| 2 | состояние: 1 STARTING, 3 PLAYING, 4 PAUSED, 5 ENDED |
| 3 | дескриптор трека, см. 3.2 |
| 4 | плеер (как в команде) |
| 5 | время запуска плеера, epoch мс (одно на плеер) |
| 7 | время паузы/конца, epoch мс; 0, пока играет |
| 8 | строка из команды (поле 40) |
| 9 | только у progress: 0 у первого после старта/перемотки, затем 1 |
| 10 | константа `{1:{1: double 10010, 2: double 19980, 3: 0.0, 4: 1}, 2: 0}` **[догадка по смыслу: границы частотной полосы, Гц]** |
| 12 | double 1.0 (громкость плеера; при приглушении диалогом не меняется) |
| 14 | диагностика (повторяющееся): `mark`, `vsid`, `buffering`, `rss_mem`, `rss_lim`, `bitrate`, `conbytes`, `conconlen`, `conpos`, `conretry`, `constate`, у ENDED ещё `played_sec` |
| 15 | константа `{2: ""}` |
| 17 | только у flag: 1 — громкость обычная, 0 — приглушена диалогом |

### 3. Правила построения

#### 3.1. Тайминги штатного `mediad` (по записям)

| Событие | Когда |
|---|---|
| STARTING | ≈14 мс после `play` |
| PLAYING | +≈7 мс, если поток уже открыт (prefetch или кэш); иначе ≈0,55–0,63 с после `play` |
| первый progress | сразу за PLAYING |
| flag | ≈290 мс после PLAYING и ≈300 мс после смены фокуса |
| progress | каждые ≈1,06 с, позиция равна реальному времени воспроизведения |
| PAUSED | ≈24 мс после `pause` |
| ENDED | при конце трека; при вытеснении новым `play` — сразу |

#### 3.2. Дескриптор события = дескриптор команды `play` с правками **[проверено побайтно, 1432 события]**

- к URL (3.2) и каждому зеркалу (3.42) дописывается `?vsid=<vsid>`; vsid = 52 символа `[a-z0-9]` + `STMx0000x` + время в секундах;
- поле 18 убирается; в поле 21 добавляется третье число `3: double −14.0` (целевая громкость);
- добавляются: 12 (целые секунды позиции), 22 (случайный uuid — новый на каждое событие), 28 (позиция, мс); по условию 6 (длительность, с;
  до готовности конвейера поля нет), 29 (`CLOCK_MONOTONIC`, мс; у STARTING до готовности нет), 30 (пустая строка);
- поля 26/27: у плеера, который `mediad` запускает **готовым** (после `prefetch` или с кэша паузы), поле 26 убирается, остаётся 27 и
  добавляется 30; у холодного запуска остаётся 26, а 27 убирается;
- после команды `crossfade` в событиях появляются 35 `{1: 1, 2: {3: 50.1, 4: 50.3}}` и 46 (= 50.1);
- у возобновлённого с паузы плеера URL, зеркала, `vsid` и `mark` берутся от прежнего открытия трека (кэш).

#### 3.3. Переходы состояний

- `pause` → PAUSED (+24 мс); плеер остаётся в кэше.
- `pause` и сразу (до ≈5 мс) `play` **другого трека** → у старого только ENDED (`pos` = позиция остановки).
- `pause` и сразу `play` **того же трека** (перемотка) → у старого PAUSED, затем ENDED.
- `play` для трека, стоящего на паузе, без `prefetch` → STARTING с `pos = offset` и «готовый» плеер (тёплый старт).
- `release` у prefetch-плеера → событий нет.
- конец трека → ENDED с `pos` = длительности; платформа сама присылает `prefetch`/`play` следующего.

## 2.5. Голос Алисы (плеер вида 2)

Ответ Алисы — не дескриптор трека, а несколько видов команд плеера `{1: 2, 2: uuid}` (полей 3 и 4 в плеере голоса нет) **[проверено побайтно, 2683 события]**:

| Команда | Поля | Смысл |
|---|---|---|
| `voice-start` | `1:{4: 5, 8: {1: id запроса, 2: «tts_play_placeholder», 3: ""}}`, `22` | начало ответа |
| `voice-chunk` | `22`, `29` = Ogg/Opus | самостоятельный поток Ogg (свои OpusHead/OpusTags, моно 48 кГц); ответ — от одного до нескольких чанков |
| `voice-eos` | `22`, `30 = ""` | чанков больше не будет |
| `release` | `22`, `31 = ""` | плеер больше не нужен (после ENDED; раньше — если ответ перебили) |

События (тип 127), верхний уровень: 1 вид, 2 состояние, 3 дескриптор, 4 плеер `{1:2, 2:uuid}`, 5 время запуска (epoch мс), 7 время конца (0, пока играет), `8: ""`,
9 (у progress: 0 у первого, затем 1), `12: double 1.0`, 14 diag, `15: ""`, 17 (у flag). Поля 10 (как у музыки) нет. Дескриптор события: поля `voice-start` плюс 12 (целые секунды), 22 (uuid, новый на каждое событие),
28 (позиция, мс) и — у ENDED и у progress/flag в состоянии PLAYING — 6 (= 0) и 29 (`CLOCK_MONOTONIC`, мс). Diag: `mark`, `vsid`, `buffering`, `rss_mem`, `rss_lim`, а `played_sec` только при pos ≥ 1000.

Тайминги штатного `mediad` (53 ответа): STARTING через ≈29 мс (13…119) после `voice-start`; PLAYING через ≈50 мс (19…119) после первого чанка, сразу за ним первый progress (позиция 0); flag через ≈263 мс после PLAYING;
progress каждые ≈1068 мс; ENDED через ≈64 мс после конца звука. **В flag и ENDED позиция — позиция последнего progress** (ENDED.pos == последний progress.pos: 53 из 53). Платформа присылает release примерно через 10–20 мс после ENDED.

## 2.6. Плеер файлов (вид 4): звонки и системные звуки

Плеер файлов играет локальные файлы из `/system/vendor/quasar/sounds/`. Два вида звуков различаются полем 1.50 стартовой команды:

- **звонок таймера и будильника** (`50: 0`) — `common/timer.wav` (по имени wav, по содержимому MP3 MPEG-1 layer III, 64 кбит/с, ≈9,25 с; во всех 32 записях
  таймеров и будильников только он) звучит по кругу, пока платформа не пришлёт `release`;
- **одноразовые системные звуки** (`50: 1`) звучат один раз, и конец сообщает сам плеер (`ENDED`); `release` платформа присылает только после него.
  Наблюдались (28.10.2026): `common/spotter_start.mp3` (звук после «Алиса», 0,58 с), `common/spotter_cancel.mp3` (отмена, 0,61 с), `common/volume_sound.mp3`
  (щелчок громкости, 0,10 с), `common/bluetooth_turning_on_jingle.opus` и `common/bluetooth_turning_off_jingle.opus` (включение и выключение Bluetooth, Ogg/Opus,
  ≈0,6 с). В каталоге лежат и другие (`notification_sound.mp3`, `calls_*.mp3`, `boot.wav`, `ru-RU/…`); тем же плеером они не наблюдались.

Команды «Начать разговор» и «Отменить разговор» в `maind --cli` звуков спотера не дают: `spotter_start.mp3` запускает только голосовая активация.

| Команда | Поля | Смысл |
|---|---|---|
| старт (`CmdFileStart`) | `1:{4: 4, 19: 0, 25: путь, 50: 0 или 1}`, `22:{1: 4, 2: uuid, 4: 1}` (у одноразовых звуков `22:{1: 4, 2: uuid}`) | начать звук (как «другая команда»: полей 4, 29, 30, 31 на верхнем уровне нет; 50 лежит внутри дескриптора и кроссфейдом не считается). Поле 1.50: `0` — по кругу до `release`, `1` — один раз (`msg.AudioCommand.FileLoops`) |
| `release` | `22`, `31 = ""` | освободить плеер: у звонка — остановить (приходит и после конца таймера, и по «стоп»/кнопке), у одноразового звука — штатно через 3…10 мс после `ENDED` |

События — тот же формат «простых» плееров, что у голоса (`quasar/mediad/plain_event.go`): верхний уровень без поля 10, `8: ""`, `15: ""`, дескриптор события — дескриптор команды плюс 12 (целые секунды позиции),
22 (uuid), 28 (позиция в мс), 6 (длительность файла **в целых секундах без округления**: у `spotter_start.mp3` 0,58 с → 0; 0, пока неизвестна), 29 (`CLOCK_MONOTONIC`, мс). Какие поля есть у какого события — таблицы ниже
(**проверено побайтно: 1060 событий звонков и 161 событие 30 одноразовых звуков, 0 расхождений**). Позиция — внутри текущего прохода файла (после конца звонка снова с нуля); в `flag` и `ENDED` — позиция последнего `progress`.

**uuid (поле 3.22):** у `STARTING` свой, а **все следующие события плеера несут один общий uuid** (у музыки и голоса он новый на каждое событие). Проверено на всех звонках и одноразовых звуках из записей.

**Событие diag (вид 5)** плеер файлов присылает один раз, как только узнал битрейт файла — сразу за первым `progress` в PLAYING: `1:5 2:3 3:{8:""} 4:плеер 14:mark 14:vsid 14:buffering 14:rss_mem 14:rss_lim 14:bitrate`
(без полей 5, 7, 8, 12, 15; проверено побайтно, 28 событий). Битрейт — **средний по заголовку Xing/Info** первого кадра MP3 (байты × 8 / длительность, как его считает разборщик MPEG в GStreamer):
`timer.wav` — 64, `spotter_start.mp3` — 80 (переменный битрейт, первый кадр 128), `spotter_cancel.mp3` — 51 (Info, кадры по 48). У файла без заголовка Xing (`volume_sound.mp3`, 4 кадра) битрейта нет совсем:
нет ни diag, ни поля `bitrate` в событиях **[вывод: у длинного файла без Xing GStreamer, возможно, сообщает битрейт позже — не проверено]**.

Тайминги звонка у штатного `mediad` (9 звонков): STARTING через ≈27 мс после команды, progress(STARTING) через ≈83 мс, PLAYING через ≈92 мс, diag через ≈107 мс, flag примерно через 330 мс от команды
(иногда дважды), первый progress сразу за PLAYING, дальше progress каждые ≈1,05 с; ENDED через ≈60 мс после `release`. Звук (PCM) запускается через ≈80 мс после команды. Громкость звонка
и нарастание громкости будильника (alarmd: старт 1, финиш 7, шаг 20 с) меняет платформа, а не `mediad`.

### 2.6б. Одноразовые звуки

Последовательность у штатного `mediad` (записи 28.10.2026): `STARTING` → `PLAYING` → один `progress` (позиция 0, поле 9 = 0) → diag (если известен битрейт) → `flag` (если звук ещё идёт;
иногда два подряд) → `ENDED` по концу звука → `release` платформы. `progress` раз в 1,05 с у них нет (звук короче секунды). Таблица полей (`fileOnceRuleViolation`, сверена с записями):

| Событие | поле 3.6 | 3.29 | поле 9 | поле 17 | diag `bitrate` |
|---|---|---|---|---|---|
| state/STARTING | нет | нет | нет | нет | нет |
| state/PLAYING | **нет** (в отличие от звонка) | **нет** | нет | нет | нет |
| progress/PLAYING | секунды (0) | есть | 0 | нет | нет |
| flag/PLAYING | секунды | есть | нет | 1 | если известен |
| state/ENDED | секунды | есть | нет | нет | если известен |

| Звук | STARTING | PLAYING | flag | ENDED | `release` платформы |
|---|---|---|---|---|---|
| `spotter_start.mp3` (0,58 с, 14 звуков) | +23…90 мс от команды | +107…229 мс | ≈210 мс после PLAYING (медиана) | ≈640 мс после PLAYING (+760…870 мс от команды), позиция 0 | через 3…10 мс после ENDED |
| `spotter_cancel.mp3` (0,61 с) | +64 мс | +134 мс | +323 мс | +803 мс | через 10 мс |
| `volume_sound.mp3` (0,10 с) | +48 мс | +107 мс | нет: звук кончился раньше | +237 мс | через 5 мс |

Под нагрузкой (8 звуков разом, когда шим при остановке отдавал их `mediad`) `mediad` присылает и `flag` в состоянии ENDED уже после конца звука; в обычной работе этого нет, автомат его не шлёт.
Играть одноразовый звук «до `release`» нельзя: release не придёт, звук зациклится (так и было в первой версии шима, docs/research/HISTORY.md, §21).
Слово «Алиса» во время звонка заставляет платформу сама послать `release` звонку (штатно): сразу за ним идёт `spotter_start.mp3`.

openmediad играет оба вида (с 28.10.2026): звонок по кругу, одноразовый звук — один раз с `ENDED` по концу звука; частые файлы раскодируются при запуске (`source.sounds.preload`).
Живая проверка через шим: щелчок громкости — STARTING +3 мс, PLAYING +5 мс, ENDED +148 мс, `release` через 5 мс; сигнал Bluetooth — PLAYING +19 мс, ENDED +620 мс.

## 2.7. Bluetooth: звук с телефона на колонку

**`mediad` в этом не участвует** [проверено 28.10.2026: ПК подключён к колонке по A2DP, играл тон; за подключение, воспроизведение и ответ Алисы поверх
на порт 9906 не пришло ни одной команды, а в iohub — ни одного кадра спектра]. Работают `platformd` (`BluetoothCapability` через D-Bus BlueZ) и BlueALSA:

```
телефон ──A2DP (SBC, 44,1 кГц)──► bluetoothd ─► bluealsa (a2dp-sink) ─► bluealsa-aplay -D bluetooth ─► pcm.bluetooth (softvol
"Bluetooth Master Playback Volume", 225 = −6 дБ) ─► speakers (plug) ─► dmix_speakers ─► hw:0,0 (громкость — аппаратный Master)
```

- Подключение источника: `Bt source connected` → `bluetooth_capability` заводит директиву `bluetooth_play` (CONTENT_CHANNEL), берёт аудиофокус, включает
  анимацию подсветки `bluetooth_playing.led`. Метаданные и состояние источника платформа читает из `org.bluez.MediaPlayer1` (AVRCP).
- Громкость: уровень платформы (0–10) переводится в громкость AVRCP (0–127) и пишется в свойство `Volume` PCM BlueALSA (`Set volume as bluetooth sink`:
  уровень 2 → 13, 4 → 25; `SoftVolume = false`, то есть громкость уходит на телефон). Громкость с телефона идёт обратно в платформу (`onVolumeChanged …
  source: bluetooth`) и меняет громкость колонки.
- Приглушение на время ответа Алисы: платформа отдаёт аудиофокус (`Free audio focus`) и через D-Bus ставит PCM BlueALSA `SoftVolume = true`, `Volume = 21`
  (BlueALSA сама уменьшает звук), после диалога — `SoftVolume = false`, `Volume = 13` и снова берёт фокус. ALSA-регуляторы при этом не меняются.
- Включение и выключение Bluetooth («включи/выключи блютуз», директивы `start_bluetooth`/`stop_bluetooth`) сопровождаются одноразовыми звуками плеера файлов (§2.6).
  «Включи блютуз» делает колонку видимой и открытой для спаривания (агент `just-works-bluez-agent` подтверждает его сам); известные устройства
  платформа хранит в `/data/quasar/data/bt_known_devices.dat`.

Отсюда для режима replace (PLAN.md, §10.4): Bluetooth-плеер «телефон → колонка» без `mediad` продолжит работать сам; движку достаточно сигналов
включения и выключения. Чтобы openmediad сам играл звук телефона (источник `btin`, приглушение своим микшером, спектр для дисплея), нужно было бы
занять место `bluealsa-aplay` — это отдельная задача.

### 2.7а. Кто запускает Bluetooth и что он умеет

Стек поднимают обычные скрипты Buildroot, до `S99quasar`; Quasar его не запускает, а только пользуется им через D-Bus (системная шина, `S30dbus`):

| Скрипт | Процесс | Заметки |
|---|---|---|
| `S39w1_bt_ant_config` | — | ссылки на прошивку и настройки радио в `/etc/bluetooth/w1/` (1 или 2 антенны) |
| `S50hci0` | `hciattach … aml` | чип Amlogic W1 на `ttyS1`, интерфейс `hci0` |
| `S51bluetoothd` | `bluetoothd -E -d` | BlueZ 5.70; `/etc/bluetooth/main.conf`: имя `Yandex.Mini3`, `AlwaysPairable = true`, `DiscoverableTimeout = 0`, `JustWorksRepairing = always` |
| `S52bluealsa` | `bluealsa -p a2dp-sink -p a2dp-source -p hfp-ag --sbc-quality=high` | BlueALSA 4.1.1, кодек только SBC (у `hfp` — CVSD и mSBC); D-Bus `org.bluealsa` — только root и группа `audio` |
| `S53bluealsa-aplay` | `bluealsa-aplay -D bluetooth -M disable -S` | `/etc/bluealsa-aplay.conf`: устройство `bluetooth`, регулятор «Bluetooth Master» = −6 дБ; играет звук любого подключённого источника |
| `S54default-bluez-agent` | `just-works-bluez-agent` | свой агент (14 КБ): подтверждает спаривание без вопросов |

Колонка **уже умеет быть источником** (профиль `a2dp-source` включён, в SDP есть «Audio Source»), а в `/usr/lib/alsa-lib/` лежат 32-битные плагины
`libasound_module_pcm_bluealsa.so` и `libasound_module_ctl_bluealsa.so`. Поэтому системный `aplay` может писать в наушники как в обычное устройство ALSA:
`aplay -D "plug:'bluealsa:DEV=<MAC>,PROFILE=a2dp'"` — кавычки вокруг аргумента обязательны (без них ALSA не разбирает запятую), с ними плагин
загружается и спрашивает BlueALSA [проверено с несуществующим адресом: «PCM not found»; с наушниками — звук идёт, 28.10.2026, §2.7б]. `arecord` тоже есть
(запись звука телефона: `arecord -D bluealsa:DEV=<MAC>,PROFILE=a2dp`).

Регуляторы громкости ALSA (карта 0): «Master Playback Volume» (numid 184, целое 0–255; `amixer` называет его «Master», это громкость
колонки, её меняют кнопки и платформа) и «Bluetooth Master Playback Volume» (numid 185, softvol звука с телефона, 225). Оба — пользовательские
элементы (большие numid). Их значение и события изменения читаются ioctl управляющего устройства `/dev/snd/controlC0`
(`system/alsactl`); подписываться на события надо до регистрации файла в epoll — иначе драйвер не будит ожидающего [проверено 28.10.2026].

Платформа знает Bluetooth только в роли приёмника: в `maind` есть «Bt source connected», `BluetoothSinkRequest` (видимость колонки как приёмника),
громкость PCM BlueALSA и аудиофокус, но нет ни одной строки о подключении наушников или колонки как источника. Наушники она не отключает, но звук
в них принимает за звук телефона и останавливает музыку — §2.7б.

Эхоподавление (`audiod`, VQE, `micChannels: 3`, `speakerChannelNamesToMusicAnalyze: raw_spk_0, raw_spk_1`) берёт опорный сигнал с аппаратной петли
усилителя (`S45hw_audio_loopback`: «Loopback Enable»; в `asound.conf` канал 6 записи — «HW feedback»). Звук, ушедший мимо динамиков (в Bluetooth или
в сеть), эхоподавление не видит: для наушников это неважно, а внешняя колонка в той же комнате будет слышна микрофонам как посторонний звук.

### 2.7б. Звук в наушники и платформа

[Проверено 28.10.2026 с наушниками ROG DELTA II: A2DP, SBC 48 кГц; транспорт BlueZ на колонке — `UUID 0000110A` (колонка — источник),
у телефона был бы `0000110B`; `Delay = 2400`, то есть наушники сообщают 240 мс своей задержки.]

**Платформа принимает любой включившийся транспорт A2DP за телефон.** Как только `org.bluez.MediaTransport1` наушников переходит в
`State = "active"` (кто-то начал писать в PCM BlueALSA), `bluetooth_capability` пишет «Bluetooth player is playing», берёт аудиофокус
(`Take audio focus`) и заводит директиву `bluetooth_play` в CONTENT_CHANNEL; музыка Яндекса (`audio_play`) отменяется через ≈2 мс, логотип вспыхивает
синим (`bluetooth_playing.led`). Транспорт снова `idle` — «Bluetooth player stops», фокус свободен, но музыка не возвращается. Направление (UUID)
платформа не проверяет. Отсюда симптом: «включи музыку» — синяя вспышка и тишина, ответы Алисы — с задержкой и обрывами (каждый ответ заново
включает транспорт).

Канал, открытый постоянно (тишина в паузах), сам по себе делает хуже: платформа снова берёт фокус примерно раз в 1,5 с и перелистывает треки.

**Ложный запуск портит и дальше.** После `bluetooth_play` платформа считает последним плеером Bluetooth: облако отвечает на «пауза/продолжить»,
«дальше», «назад» директивой `player_continue` и т. п., а `BluetoothCapabilityPreprocessor` переписывает её в `bluetooth_player_resume` /
`_next` / `_prev` — команды уходят несуществующему телефону. Проходит, только когда снова запустится музыка Яндекса («включи музыку»).

**Адресный сигнал «простаивает»** исправляет уже случившееся: `org.freedesktop.DBus.Properties.PropertiesChanged` с путём транспорта и телом
`("org.bluez.MediaTransport1", {"State": <"idle">}, [])`, отправленный не всем, а только соединениям платформы (поле `DESTINATION` — уникальное имя;
у `maind --platformd` их три, находятся через `ListNames` и `GetConnectionUnixProcessID`). Платформа через ≈100 мс пишет «Bluetooth player stops» и
отпускает фокус; BlueZ, BlueALSA и остальные клиенты шины сигнала не видят, звук идёт дальше. Но музыка уже отменена.

**Адресное «транспорт удалён» не даёт ложному запуску случиться.** Платформа держит на каждый транспорт объект-прокси (`bluez_impl::MediaTransport`,
заводит его по `InterfacesAdded`, в журнале — «No such property "Volume" at start …»). Сигнал `org.freedesktop.DBus.ObjectManager.InterfacesRemoved`
от пути `/` с телом `(<путь транспорта>, ["org.bluez.MediaTransport1"])`, отправленный тем же адресно, заставляет её забыть объект: дальнейшие
`State = "active"` этого транспорта она не видит вовсе [проверено 28.10.2026: поддельное «active» до удаления — «is playing», после — тишина;
настоящее переподключение наушников посреди трека — музыка не остановилась, ни одного «is playing»]. Отправлять надо после её `InterfacesAdded`
(иначе она заведёт объект заново) и до первого включения: на колонке между ними ≈80 мс.

Как это сделано в `sink/bluetooth`: пока выбранные наушники подключены, держится один вывод (`aplay` в PCM BlueALSA) со смесителем — потоки движка
складываются порциями по 20 мс, в паузах идёт тишина. Каждый новый транспорт в наушники платформе «удаляется» сразу, как появился, раньше открытия
канала (`bluez.Client.ForgetTransport`); если он к этому моменту уже активен (демон перезапустился при открытом канале) — сначала «простаивает».
Платформа перезапустилась (другой PID) — сообщается заново. Звучащие потоки движок при подключении переводит в наушники посреди трека.

**Громкость.** Платформа хранит уровень 0–20 и переводит его в Master по таблице `platformToAlsaMap` из `quasar.cfg`
(`volume_capability.volume_manager_settings`, у bergamot `{"0": 0, "1": 33, "20": 255}`, между точками линейно: 12 → 162, 13 → 173, 14 → 185).
Громкость Bluetooth-устройства она ведёт через тот же объект транспорта, что и его звук: при смене уровня не с устройства (кнопки колонки,
голос) ставит `MediaTransport1.Volume = round(уровень·127/20)` («Set volume as bluetooth sink»: 2 → 13, 4 → 25, 6 → 38, 9 → 57) — BlueZ передаёт
её наушникам по AVRCP; изменение `Volume` с устройства (колесо и кнопки наушников) читает как `round(громкость·20/127)` («onVolumeChanged …
source: bluetooth»), ставит себе и показывает на экране. Это работает и для наушников — если транспорт ей виден. Поэтому в режиме speaker транспорт
наушников после включения канала ей возвращается простаивающим (ShowTransport), и громкость синхронизирует она сама; движок только выравнивает
наушники по колонке при подключении. Программную громкость BlueALSA (`SoftVolume`) движок выключает: с ней звук приглушался дважды — наушниками
и BlueALSA [проверено 28.10.2026: `dbus-monitor` — «громкость 3» → платформа `Set Volume 38` транспорту, наушники ответили 38; громкость с
наушников 45 → уровень 7; движок не вмешивается, скачков нет]. Пока транспорт был спрятан совсем, громкость наушников до платформы не доходила
(ни уровня, ни экрана); до этого движок писал громкость сам, линейно по Master, и вместе с округлениями платформы и шагами наушников уровень
уезжал к 14 из 20 (70 %).

**Кнопки наушников.** Свой плеер (MPRIS) колонка в BlueZ не регистрирует, поэтому команды AVRCP от наушников BlueZ отдаёт устройству ввода
«<имя> (AVRCP)» (uinput, у ROG DELTA II — `/dev/input/event2`): PLAY → `KEY_PLAYCD`, PAUSE → `KEY_PAUSECD`, FORWARD → `KEY_NEXTSONG`,
BACKWARD → `KEY_PREVIOUSSONG`, STOP → `KEY_STOPCD`. Платформа это устройство не читает. `sink/bluetooth` читает его сам и отдаёт команды платформе
от имени клиента `aliced`, как пункты `maind --cli` (`quasar/control`): регистрация `EndpointStorage_` (метод 1) и `PlaybackControlCapability`
(метод 13) с видом 2 — пауза/продолжить (с флагом 2 = 1: можно попросить музыку), 6 — дальше, 7 — назад, 1 — пауза; источник `"Keyboard"`.
Платформа выполняет их как нажатие кнопки (`playback_next.Keyboard` → `audio_client_next_track`) [проверено 28.10.2026 и имитацией, и
настоящими кнопками]. Размер `struct input_event` зависит от разрядности процесса: 64-битный демон читает по 24 байта, 32-битный shell колонки
пишет по 16.

**Громкость динамиков при наушниках (`sink.bluetooth.hold_speaker`, по умолчанию да).** Уровень у платформы один, и голос Алисы на
динамиках звучал бы так же, как музыка в наушниках. Пока платформа ведёт громкость наушников, движок держит Master на значении до подключения
(её изменение сразу возвращает; запись регулятора — ioctl `SNDRV_CTL_IOCTL_ELEM_WRITE`, `system/alsactl`). Наушники отключились — уровень
платформы возвращается текстовым запросом «громкость N» (голосом платформа ставит только чётные уровни: `sound_set_level`, N·2), иначе первое
же нажатие кнопки поставило бы динамикам уровень наушников. Через транспорт отключившихся наушников уровень не передать: на `InterfacesAdded`
платформа идёт к объекту BlueZ, а его уже нет («BluezBluetooth raise exception: …UnknownObject») [проверено 28.10.2026: громкость наушников
70 → уровень 11, Master остался 68; отключение → «громкость 2» → уровень 4].

**«Выключи блютуз».** Платформа на `stop_bluetooth` только прячет колонку («Set visibility. discoverable: 0, connectable: 0»), подключённые
устройства не трогает — наушники играли бы дальше. Директивы ответа видны в рассылке `aliced` (AliceState, у этих — пустой номер запроса);
по `stop_bluetooth` выход отключает наушники и не подключает их сам, по `start_bluetooth` — снова подключает [проверено 28.10.2026].

**Анимация паузы.** Анимации «пауза», «дальше», «продолжить» приходят из облака (`draw_animation_directive` через `LedCapability` в ответе
на запрос). Локальная команда `PlaybackControlCapability` ставит паузу без облака (`audio_stop`) — без анимации. Поэтому пауза с кнопки
наушников, пока играет музыка, отправляется текстовым запросом «поставь на паузу» (AliceCapability, метод 8, вид 0, `text_input`; сборщик
`wire.TextInput` совпадает с кадром `maind --cli` из mdbg1.pcap побайтно) — с анимацией, как голосом; продолжение, «дальше» и «назад» —
локальными командами (они сами спрашивают облако).

### 2.7в. Звук телефона через openmediad (компонент `btin`, опытный)

Штатно звук телефона играет `bluealsa-aplay` (§2.7): PCM BlueALSA приёма A2DP (`A2DP-sink`, режим `source` — из него читают) → ALSA-устройство
`bluetooth` (softvol −6 дБ) → динамики. PCM BlueALSA принимает одного клиента, поэтому `btin` на время работы останавливает службу
(`/etc/init.d/S53bluealsa-aplay stop`; rootfs не меняется) и при остановке демона запускает её снова — даже если её остановил прошлый,
оборванный запуск [проверено 28.10.2026: `stop` — служба снова работает, `start` — остановлена]. Когда PCM телефона `Running`, `btin` читает его
системным `arecord` (`plug:'bluealsa:DEV=<адрес>,PROFILE=a2dp'`, S16LE в формате PCM) и играет как поток движка класса music: приглушение на время
диалога — по `focus.duck_gain`, спектр — для дисплея, выход — по `[route] music`; громкость по умолчанию −6 дБ, как у штатного пути.

Управление остаётся платформе: она видит звук телефона как раньше (Bluetooth-плеер, логотип), передаёт ему «пауза», «дальше», громкость по AVRCP.
Своё приглушение на время диалога она делает программной громкостью PCM (`SoftVolume = true`, `Volume = 21`, §2.7) — `btin` сразу возвращает её
к полной (127), чтобы звук не приглушался дважды; после диалога платформа сама ставит `SoftVolume = false` и громкость телефона.

Проверено с телефоном 28.10.2026: BlueALSA ставит `Running` и без клиента — поток открывается через ≈40 мс после «Bluetooth player is
playing»; платформа шлёт шиму аудиофокус диалога и во время звука телефона — движок приглушает его по `duck_gain`; спектр рисуется. Своё
приглушение платформа делает так: `SoftVolume = true`, затем `MediaTransport1.Volume = 21` (BlueZ передаёт его телефону), после диалога —
`SoftVolume = false` и прежняя громкость телефона. `btin` выключает только `SoftVolume` (громкость не трогает: BlueALSA передала бы её телефону,
и ползунок на телефоне уезжал бы в максимум — так и было в первой версии). Колонка не держит телефон и наушники одновременно: подключение
наушников выбило телефон, поэтому, пока подключён телефон, наушники сами не подключаются.

## 3. Спектр для дисплея (iohub)

Платформа рисует спектр последнего объявленного потока и не дольше 15 с после его «начат» («Stop spectogram by timeout» ровно через
15 с, хотя кадры идут дальше; длительность — из её облачных настроек, `SpectrogramAnimationManager::subscribeOnConfig`). Когда Алиса
договорила, поток спектра голоса останавливается, и анимация гаснет совсем. Каждое «начат» или «продолжен» отсчёт сбрасывает
(`onSpectrumStartResume`). С настройкой `spectrum.always` движок объявляет поток музыки заново (служебное «начат» с тем же номером): раз в
10 с, пока она играет (кроме времени диалога и голоса Алисы — их анимацию не перебивает), после остановки спектра голоса и после конца
приглушения [проверено 28.10.2026: «Spectrum started» каждые 10 с, гашения нет весь трек].

`mediad` — клиент iohub (порты 9903 и 9910); сервер — `platformd`. Клиент при подключении **ничего не отправляет**, сервер сам шлёт
служебные сообщения (их нужно вычитывать). Для визуализации `mediad` шлёт на 9903 сообщения типа 85 с полем **46** (вывод по записям)
25 раз в секунду (по одному на 40 мс), `iohub` рассылает их подписчикам на 9910 (по записи — двум). **[проверено побайтно: 3001 кадр данных
и 39 служебных пересобраны из полей без расхождений]**

Поле 46:

| Поле | Данные | Служебное |
|---|---|---|
| 1 | момент, **когда звук прозвучит**, Unix-наносекунды: у `mediad` кадр уходит раньше метки на ≈0,29 с (приход − метка: медиана −0,29 с, от −0,30 до +0,06 с; в первых кадрах после старта потока ≈ 0). Метка в прошлом платформа не рисует | — |
| 2 | 40000000 (интервал, нс) | — |
| 3 | 48000 (частота) | — |
| 4 | 513 значений float32 LE: уровень в дБ (≥ −80) | — |
| 5 | −80 как int64 (в varint 18446744073709551536) | — |
| 6 | 0 | 1 старт потока, 2 остановка, 3 продолжение после паузы |
| 7 | идентификатор потока (у mediad `CLOCK_MONOTONIC`, нс, на старте) | то же |
| 8 | 0 музыка, 1 голос Алисы | то же |

Расчёт значений — как у GStreamer `spectrum bands=513 threshold=-80 interval=40000000`: **окно Хэмминга** 0,54−0,46·cos(2πi/(N−1)), N = 1024;
вход — среднее двух каналов / 32767 **после** нормализации и приглушения; **один БПФ на интервал по его первым 1024 отсчётам**
(остальные 896 не используются); мощность `|X|²/N²`, перевод `10·lg`, не ниже −80. **[проверено: разброс 0,02–0,05 дБ на двух треках]**
У голоса (`8 = 1`) вход — моно-PCM декодера Opus **вместе с выброшенными pre-skip отсчётами** (312 в начале каждого чанка), без нормализации: разность со штатным 0,000 дБ, разброс 0,032 дБ **[проверено]**.
Остановка и пауза (`6:2`) приходят примерно через 0,4 с после прихода последнего кадра (≈0,1 с после его метки), то есть когда последний кадр уже прозвучал. Старт потока (`6:1`) идёт до первого кадра; при паузе — `6:2`; при возобновлении — `6:3` с тем же потоком; при смене трека у старого `6:2`,
у нового `6:1`. У голоса Алисы свой поток (`8:1`); его шлёт тот, кто играет голос (openmediad с компонентом `tts`). Во время звука с телефона по Bluetooth спектра нет совсем (§2.7).

Прочее на iohub во время музыки (не воспроизводится шимом, нужны платформе сами): поле 56 — копия состояния плеера (≈2/с, `iohub_clients`),
поле 34 — состояние SDK (≈1/с); их формирует `platformd` по событиям плеера.

## 4. Диалог Алисы (для журнала)

`AliceState` (тип 3, порт 9875): поле 1 — состояние (0 IDLE, 1 LISTENING, 2 SPEAKING, 3 BUSY), 2 — распознанная фраза, 15 — признак окончательности,
3 — ответ облака (текст и директивы). Шим только читает его наблюдателем для отладочного журнала. Ответ на «включи музыку» содержит директиву
`process_smart_volume_directive` (в `quasar.cfg` включён `smart_volume` с порогами по шуму) — возможная причина самопроизвольных изменений громкости **[догадка]**.
