## 1. Цель

Колонка остаётся умным устройством и играет Spotify, а потом и другие сервисы:

- по прямым запросам («включи такую-то песню») и размытым («включи музыку»);
- с лайком, дизлайком, паузой, «дальше»;
- с Плюсом и без него: автор платит не всегда, а у части пользователей его нет вовсе;
- с подбором на «включи музыку», который можно заменить в коде: рекомендации Яндекса — главная причина ухода автора на Spotify;
- в двух режимах: Яндекс по умолчанию и Spotify Connect в фоне; Spotify по умолчанию, но выбор колонки в приложении Яндекс Музыки работает штатно.

## 3. Что уже известно

**Колонка видит решение LLM** (автор предполагал обратное). В `prefetch`/`play` открыты название, исполнитель и контекст вроде «Моя волна»
(BUS-PROTOCOL.md, поле 1.9), полный JSON директивы лежит в поле 1.7, а ответ облака — в `AliceState` 3.5. Финальный текст STT приходит в `AliceState` на
0,6–1 с раньше ответа (`msg.go:88-114`, одна запись, QUASAR-PROTOCOL.md:352-367). Лайк и дизлайк нигде не записаны.

**Звук Spotify.**

- librespot и go-librespot на новых аккаунтах получают отказ в аудиоключе. Мейнтейнер librespot: [«New accounts can't use AES. Sadly a dead-end for them.»](https://github.com/librespot-org/librespot/issues/1649#issuecomment-6083823859)
  Граница, по [Music Assistant](https://www.music-assistant.io/music-providers/spotify/), примерно декабрь 2024. Ожидание для аккаунта автора: отказ почти на всех треках [вывод, без статистики].
- [Spotify Soloist](https://developer.spotify.com/blog/2026-08-13-introducing-spotify-soloist) (с 13.08.2026) — официальный закрытый движок того же уровня, что настольное приложение.
  Сборки есть для Linux aarch64, armv7l и x86_64, Windows x86_64 и Mac на Apple Silicon. [Каждая сборка истекает через 90 дней, код выхода 10, распространять нельзя](https://developer.spotify.com/documentation/soloist/reference/downloads-and-updates).
  На Linux нужен PipeWire или PulseAudio. Запуск требует API-ключа из Developer Dashboard (его выпускает аккаунт с Premium), затем сопряжение из приложения Spotify в той же сети ([начало работы](https://developer.spotify.com/documentation/soloist/tutorials/getting-started)).
- У Soloist нет поиска и лайка, команды или флага отключения autoplay в документации нет [вывод], отдельного события конца трека нет, очередь нельзя очистить ([WebSocket API](https://developer.spotify.com/documentation/soloist/reference/websocket-api)).
- [mini2-spotify](https://github.com/AvelcFox/mini2-spotify) запускает Soloist на Станции Мини 2 со своей `libpulse` в `aplay` и заявляет 18–25 МБ. Это только заявление автора и другое устройство.

**Web API Spotify** (нужен для поиска и лайка). [С февраля 2026](https://developer.spotify.com/documentation/web-api/references/changes/february-2026): поиск до 10 результатов, нет Top Tracks и пакетных запросов;
рекомендации закрыты [с 2024](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api). Каждый пользователь регистрирует свой Client ID. Redirect только HTTPS или `127.0.0.1`.
[Refresh-токен живёт 6 месяцев и не продлевается](https://developer.spotify.com/documentation/web-api/tutorials/refreshing-tokens). Публичного дизлайка не найдено.

**Условия.** [Developer Policy](https://developer.spotify.com/policy) III.3 запрещает голосовое управление Spotify. Страна аккаунта должна быть страной проживания. Поэтому компонент `spotify` вне стандартной сборки, ставится самим пользователем,
README честно описывает риск, совместимость с правилами не заявляется. Это нужно решить и как вопрос к публикации проекта: в корне репозитория ещё нет `LICENSE`.

**Без Плюса** [вывод]: `audio_play`, скорее всего, не приходит, и перевод не получает трека. [Справка Яндекса](https://alice.yandex.ru/support/ru/station/settings/services): остаются радио, будильник со стандартной мелодией, навыки, умный дом, Bluetooth.

**Что брать из [spotiya](https://github.com/klockky/spotiya)** (MIT): быстрые фразы через `CommandSpotterCapability`, срок жизни намерения и счётчик эпох, прекращение повторов при окончательном отказе входа, логику захвата кнопок (`EVIOCGRAB`), корпус фраз для тестов.
Не брать: опрос паузы каждые 500 мс (мы владеем шиной), перехват всех «включи X», статус READY при отказе в ключе, тишину при ошибке.

**PlayPlay в проект не входит** независимо от риска для аккаунта автора. Это эмуляция DRM-декодера с фрагментами кода Spotify: такой код нельзя распространять под лицензией проекта, и это обход защиты контента, а не вопрос личного риска. Ни код, ни инструкция, ни адаптер к нему в проект не попадают.

## 4. Варианты

Выбор идёт по четырём осям, несовместимые сочетания указаны в §5.4. Connect (выбор колонки в приложении Spotify) — не вариант, а обязательная часть любого решения с резидентным движком.

### Ось А. Откуда звук Spotify

| Вариант | Что это | Сильная сторона | Слабая сторона | Закрывается опытом |
|---|---|---|---|---|
| **А1** Soloist на колонке | Сборка armv7l, своя `libpulse` → FIFO → `engine.Source` | Официальный, должен играть на новом аккаунте. Всё работает через движок: приглушение, спектр, маршруты | Запуск на Мини 3 не доказан, нужна своя `libpulse`, 90 дней, управление через WebSocket без авторизации (только loopback) | О1, О3 |
| **А2** go-librespot на колонке | Отдельный процесс, REST и события, FIFO в S16LE. Лицензия GPL-3: только отдельным процессом | Управляем: `disable_autoplay`, станции по URI, `play_origin`, события ошибок | На аккаунте автора, скорее всего, не заиграет. Приватные API | О2 |
| **А5** librespot на колонке | Отдельный процесс, `--backend pipe` → FIFO. Лицензия MIT. Готовый бинарник — приёмник Connect без локальной команды запуска трека, поэтому запуск либо через Web API (`PUT /me/player/play`), либо своей обёрткой на Rust через `Spirc`, как в spotiya | Большое сообщество, вероятно меньше памяти: 6,7 МиБ в простое у spotiya на Мини 2 (без воспроизведения, замера на Мини 3 нет) | Тот же отказ в ключе. Web API — круг через облако Spotify, обёртка — второй язык в проекте | О2 |
| **А3** Soloist на другом устройстве | Raspberry Pi или домашний компьютер, PCM по сети в движок (`net-in`, фаза 11) | Снимает риск памяти и glibc | Нужен второй прибор; не решение «для всех» | О1 |
| **А4** Телефон по Bluetooth | Готовый `bt-in`: звук Spotify с телефона через движок | Работает сейчас | Нет голосового выбора трека, это запасной способ слушать | — |

### Ось Б. Как запрос становится музыкой

| Вариант | Механика | Что слышно | Пауза, «дальше» | Плюс |
|---|---|---|---|---|
| **Б1** Родная сессия | Фраза → шлюз голоса → свой проигрыватель. Платформа о звуке не знает | Сигнал, затем музыка | По фразам. Кнопки под вопросом | Не нужен |
| **Б2** Перевод 1:1 | Облако выбирает трек, движок находит его в Spotify и играет под автоматом | «Включаю», затем та же песня | Готовые команды шины | Нужен |
| **Б3** Носитель-такт | Как Б2, но играет своя лента, а `play` и ENDED от облака служат тактами | «Включаю», затем своя музыка | Готовые команды шины | Нужен |

- **Основной кандидат — Б1**, потому что он единственный работает без Плюса и не приписывает своих треков Яндексу.
- **Б2** разрешён только когда звучит та же песня, что считает играющей сервер. Лайк и «что играет» при этом верны.
- **Б3** проигрывал в проекте: история Яндекса постоянно засоряется, лайк и «что играет» указывают мимо, платформа может не терпеть другую длительность.
  Опыт дешёвый и даёт большой выигрыш в управлении, поэтому он идёт в пробу, если платформа пройдёт О5.
- Промах или сбой провайдера в Б2 и Б3 — тот же трек из Яндекса.

### Ось В. Кто подбирает на «включи музыку»

| Вариант | Что это | Подвох |
|---|---|---|
| **В1** Своя лента | Семя → источники кандидатов → поиск в Spotify → память и фильтры → один трек в очереди. Источники заменяемы | Качество зависит от источников (ниже) |
| **В2** Autoplay Spotify | `play` семени и дальше сам Spotify | Нет фильтра и памяти, нельзя заменить, новый аккаунт. Используется как страховка, пока не докажет обратное |
| **В3** Волна Яндекса | Перевод каждого трека 1:1 | Вкус Яндекса, нужен Плюс. Выключено по умолчанию |
| **В4** Внешняя программа | `rec-exec` (JSON через stdin/stdout) или `rec-http` (свой сервер, своя модель) | Пишет сам пользователь. Это и есть замена подбора без пересборки |

Источники для В1. Пробы от 31.10.2026 шли через Финляндию, из России доступность **неизвестна**:

| Источник | Проба | Подвох |
|---|---|---|
| Deezer `artist/radio`, `artist/related` | Хорошо и на «Кино», и на Radiohead, без ключа | [Только некоммерчески](https://developers.deezer.com/termsofuse). Сервис объявил об уходе из РФ в 2022 |
| ListenBrainz `similar-artists` | Хорошо по «Кино» | Личный токен; `similar-recordings` по «Кино» пуст |
| Last.fm `getSimilar` | На сайте хорошо, API не проверен | Ключ у каждого свой, [только некоммерчески](https://www.last.fm/api/tos) |
| Библиотека Spotify (`/me/top`, `/me/tracks`) | На новом аккаунте пусто | Только резерв, открытий не даёт |

Семя выбирается взвешенным случаем из: запроса, текущего трека, лайков, истории, библиотеки, настройки `favorites`. На новом аккаунте работает только `favorites`, поэтому её нужно заполнить; в шаблоне настроек имён исполнителей быть не должно.
Трек Яндекса как семя на голую «включи музыку» запрещён. Логику пула, памяти и разнесения исполнителей берём из [Music Assistant](https://github.com/music-assistant/server/blob/beecc71/music_assistant/controllers/player_queues/managed_pool.py), переносится только алгоритм.

Семя бывает трёх видов: исполнитель или трек, тег, текст. Настроение и жанр («включи рок», «что-нибудь весёлое») сводятся к тегу словарём в настройках: источники выше устроены от исполнителя, а рекомендации Spotify закрыты. Источник тега — Last.fm `tag.getTopTracks` (не проверен, входит в О8), запасной — поиск плейлиста в Spotify по тексту. Остаток фразы сначала ищется как исполнитель, при промахе звучит «скажите, кого включить».

### Ось Г. Как понять фразу

Корзина определяется по тексту: он приходит рано и есть всегда. Для корзины 2 окончательное решение принимается по ответу облака.

1. **Точная фраза**, совпадает целиком: управление при активной сессии, лайк, дизлайк, «что играет», голая «включи музыку», «в спотифай». Действие сразу.
2. **Кандидат** `включи|поставь|запусти|сыграй + X`: голос удерживается от первого чанка ответа, не дольше `voice_gate`. Решает ответ: `audio_play`, музыкальный отказ или что-то чужое.
3. **Остальное:** не трогаем. Сюда входит умный дом, и сценарии автора нужно явно перечислить как исключения.

Корзина 1 зависит от настроек:

- Голая «включи музыку» идёт в Алису, если `default` и `fuzzy_player` пусты, либо при Плюсе и `strategy = tick`, либо при Плюсе и `chain = ["cloud"]`. Иначе она идёт в `Picker`.
- Лайк, дизлайк и «что играет» перехватываются при владельце `native`, `connect`, `carrier`. При `cloud` и переводе Б2 они идут в Алису: сервер считает играющей ту же песню. В Б2 лайк дополнительно зеркалится в Spotify.

Если отказ без Плюса окажется неотличим от других ответов (О4), сразу срабатывают только фразы с маркером («песню», «трек», «группу», «альбом», «плейлист») и «в спотифай». Голое «включи X» при `plus = no` идёт в Алису. Тогда критерии §7 и фазы 9 без Плюса читаются как «включи песню <название>» и «включи группу <название>», а снижение требования подтверждает автор. Правило сомнения: не можем приписать голосу — значит Яндекс.

Глушит Алису в первую очередь **шлюз голоса**: шим не проигрывает чанки ответа и сообщает платформе конец (`mediad/voice.go`). `CancelDialog` только помогает: в кадре нет номера запроса (`wire.go:188-190`), и опоздавшая отмена убьёт следующий диалог, поэтому отправлять её можно лишь пока последний `AliceState.7` равен нашему запросу и состояние LISTENING или BUSY.

## 5. Общий каркас

Каркас один на все варианты: варианты меняются настройками, а не ветками. Только так их можно честно сравнить на одной колонке.

### 5.1. Три роли

| Роль | Вопрос | Вход | Выход | Чего не знает |
|---|---|---|---|---|
| Источник намерения | Что человек хочет? | Фраза, ответ облака, команды шины | `Intent` | Кто подбирает и играет |
| Подборщик | Какой трек следующий? | Семя, курсор, память | Партия кандидатов | Quasar, Алису, шину, Плюс |
| Проигрыватель | Чей звук? | Ссылка на трек | PCM и события | Фразы, откуда трек |

### 5.2. Единый владелец звука

Состояния: `none`, `cloud` (играет Яндекс), `carrier`, `native`, `connect`. Имя сервиса в ядре запрещено архитектурным тестом. Арбитр — единственное место, где они меняются. Сейчас арбитража нет: `NewStream` никого не закрывает (`engine.go:194-214`), поэтому без него потоки смешаются.

| Событие | Что делает арбитр |
|---|---|
| Новый голосовой запуск | Названный сервис → звучащая сессия из приложения → `default`. Сессия на паузе звучащей не считается |
| Запуск без доказательств голоса (приложение, будильник, сценарий, Глагол, мультирум) | `cloud`; провайдер на паузу |
| Выбор колонки в приложении Spotify | `connect`; плеер автомата получает PAUSED |
| Сессию Spotify забрал другой клиент | В `none`, а не «конец трека»: иначе возникает цикл с облаком |
| Звонок будильника или таймера | Приглушение, а не пауза; «стоп» не перехватывается, пока идёт звонок |
| `native` запущена, а `pause` от платформы не пришёл за 300 мс | Автомат сам отправляет PAUSED с текущей позицией этого плеера и закрывает свой поток. Голос не трогает, штатному `mediad` ничего не передаёт. Новый метод `PausePlayer(id)` выделяется из `Handoff` |

Обязательно: счётчик поколений (запоздавший `stop` от `go Close`, `audio.go:303`, не должен убить новый трек), один владелец громкости (`Play` перезаписывает громкость класса, `audio.go:251`), OR двух сигналов приглушения (`focus` и `AliceState.Kind().Active()`), состояние владельца на `/data` для перезапуска.

### 5.3. Контракт

`internal/core/music`, только типы и алгоритм: архитектурный тест запрещает имена компонентов в ядре, и умолчания приходят из самих компонентов.

```go
// Уровень 0: голос, перевод, откат. Выше — по приведению типа, как Seeker и Waker в engine.
type Provider interface {
    Info() Info     // имя, алиасы для фраз, формат; формат проверяется без panic
    Health() Health // ok, needs_setup, auth_failed, no_premium, audio_refused, engine_expired, offline, rate_limited
    Search(ctx context.Context, q Query, limit int) ([]Item, error)
    Open(ctx context.Context, it Item, offsetMs uint64) (Playback, error) // идемпотентно: prefetch и play вызывают его дважды
    Events() <-chan Event                                                 // Origin: self или remote
}
type Playback interface { // сверить с engine.Source при написании
    engine.Source
    Pause() error; Resume() error; Seek(ms uint64) error; Stop() error
}
type Liker interface{ Like(ctx context.Context, it Item, liked bool) error } // уровень 1; false снимает лайк, дизлайк только через Picker.Report
type Remote interface { // уровень 3: сессия из приложения
    Session() Playback
    Next() error; Prev() error
}

// Подборщик. Уровень 2 — источник, реализуемый компонентом.
type Source interface {
    Info() SourceInfo // имя, DefaultOrder, NeedsPlayer
    Next(ctx context.Context, r Request) (Batch, error) // ErrEmpty, ErrAuth, ErrQuota, ErrUnavailable
}
type Picker interface {
    Start(ctx context.Context, s Seed) error
    Pop(ctx context.Context) (Next, error) // трек, делегирование проигрывателю или конец
    Observe(it Candidate)                  // трек заиграл без нашего заказа (autoplay)
    Report(f Feedback)                     // лайк, дизлайк, пропуск, дослушан
}
```

Поля `Item`, `Query`, `Event`, `Seed` записываются первым пунктом этапа 1. Уровни провайдера: **0** поиск и поток, **1** лайки, **2** своя лента, **3** сессия из приложения. Провайдеры сначала компилируются в движок, хост подпроцессов (stdio JSON-RPC, PCM через отдельный дескриптор, манифест, подпись) — когда появится первый внешний автор.

Очередь Soloist: `add_to_queue` принимает трек, очистить её нельзя, поэтому в очереди всегда один трек. Следующий ставится после `track_changed`. Источник узнаётся из `get_queue` или `queue_changed` (`upcoming[].source`, `previous[].source`): в самом `track_changed` его нет. При `autoplay` пул синхронизируется заново. Если очередь не сдерживает autoplay (О1), следующий шаг — `play` следующего трека у конца текущего.

### 5.4. Настройки для проб

```toml
[music]
default      = ""        # "" = Яндекс как сейчас; иначе имя провайдера
strategy     = "native"  # native (Б1) | translate (Б2) | tick (Б3): действует при наличии audio_play
fuzzy_player = ""        # кто играет ленту; "" = default
plus         = "auto"    # auto | yes | no
on_refused   = "player"  # player | alice
on_miss      = "cloud"   # cloud: если трек облака есть, играет он, иначе как speak | next | speak
min_score    = 0.8
voice_gate   = "400ms"   # подбирается по записям О4

[recommender]
chain     = []           # пусто = DefaultOrder компонентов (В1); "autoplay" = В2; "cloud" = В3; "exec", "http" = В4
favorites = []

[spotify]
enabled   = false        # без него движок не запускается, и Connect тоже
engine    = "soloist"    # soloist (А1) | go-librespot (А2) | librespot (А5) | remote (А3)
connect   = "always"     # always | off
client_id = ""           # ключ Soloist и токены только файлами 0600
```

Значения по умолчанию оставляют колонку такой, как сейчас: без провайдера `BackendRouter` не ставится, и никаких новых веток не выполняется.

Правила сочетаний:

- `translate` переводит только `audio_play` конкретного трека, а `audio_play` волны или контекста уходит в `Picker` с семенем из запроса. Исключение — `chain = ["cloud"]`, тогда переводится всё.
- `cloud` требует `translate` и Плюса. Иначе `doctor` предупреждает, и цепочка идёт к следующему источнику.
- Без Плюса `translate` и `tick` работают как `native`. В таблице §7 такие строки отмечаются как совпадающие с Б1.
- Режимы автора: **Я** — `default = ""` при `[spotify] enabled = true`, **С** — `default = "spotify"`.

## 7. Как сравнивать варианты

Живые комбинации определяются опытами, ожидаемо: А1+Б1+В1 (основная), А1+Б1+В2, А1+Б1+В4 (простой скрипт `rec-exec`), А1+Б2+В1 (точные запросы с Плюсом), А1+Б2+В3 (с Плюсом), А1+Б3+В1, и то же с А2, А3 или А5, если они выжили. Переключение: `openmediad config set`, затем `openmediad restart`.

Обязательный прогон — оба режима автора. **Режим Я** (`default = ""`, `[spotify] enabled = true`): голос работает как без проекта, «в спотифай» и Connect уводят в Spotify. Пока сессия Connect звучит, «включи X» без названия сервиса остаётся в Spotify; после паузы или конца сессии такой запуск снова идёт в Яндекс, а во время сессии Яндекс включается только если назвать его во фразе. **Режим С** (`default = "spotify"`): действуют строки таблицы ниже. Без Плюса строка «Выбор в приложении Яндекса» считается пройденной, если Яндекс честно отказал, а Spotify не запустился.

Для каждой комбинации заполняется таблица, с Плюсом и без него:

| Сценарий | Что считаем успехом |
|---|---|
| «Включи <песню>», есть и нет у Яндекса | Звучит именно она, старт до 3 с |
| «Включи <песню>», которой нет в Spotify | С Плюсом — трек Яндекса или «не нашла» по `on_miss`, без Плюса — «не нашла». Без молчания |
| «Включи Кино», «включи рок», «включи что-нибудь весёлое» | Смысл сохранён, в ленте нет явного мусора |
| «Включи музыку», 2 часа | Без повторов, вкус устраивает автора (оценка от 1 до 5) |
| Пауза, продолжи, дальше, назад, перемотка | Срабатывает с первого раза, Алиса не мешает |
| Лайк, дизлайк | Лайк виден в Spotify. Дизлайк пропускает трек и заносит его в локальный бан; при В2 трек из бана сразу пропускается через `Observe` |
| «Что играет» | Правда или честная фраза |
| Кнопки на корпусе | Управляют текущим источником, не запускают Яндекс |
| «Включи свет», таймер, вопрос Алисе, радио | Работают как обычно, никаких ложных захватов |
| Будильник во время музыки | Звонит всегда, музыка затем возвращается |
| Выбор в приложении Spotify и обратно голосом | Без наложения звука |
| Выбор в приложении Яндекса | Яндекс играет штатно, голос не уводит в Spotify |
| Звонок телефону на тот же аккаунт Spotify | Нет цикла, понятный статус |
| Обрыв сети, истёкший токен, истёкшая сборка | Говорит о причине, статус верный, колонка не молчит вечно |
| `kill -9` демона | Нет второго экземпляра, звук возвращается |
| Память за сутки | `MemAvailable` > 40 МБ всё время |

Решает автор, но правило одно: Плюс не должен быть обязательным, и вкус подбора важнее анимаций.

### 10.5. Модуль `spotify-soloist` (этап А, 01.11.2026)

Опыт превращён в компонент движка ([internal/components/spotify-soloist](../internal/components/spotify-soloist/README.md)): подключается тегом сборки,
ставится и настраивается командой `openmediad spotify`, играет через движок (приглушение под Алису, спектр, маршруты `[route]`).

**Решения.**

- Лицензия проекта — MIT (`LICENSE`); Soloist не распространяется (скачивается пользователем с CDN Spotify при `setup`), glibc 2.41 качается из
  пакета Debian с зафиксированным sha256 (LGPL, файлами рядом, заменяема), шим — свой код.
- `abi.cp15_barrier = 2` компонент выставляет сам при каждом запуске (`fix_cp15`); согласие пользователя — само включение компонента в сборку:
  предупреждение (`registry.Info.Notice`) печатает `tools/build`, оно есть в паспорте, `components -v`, шаблоне настроек и README; `doctor` проверяет параметр.
- Каждый движок Spotify — отдельный компонент с общими кирпичами в `libs/`: `pcmstream` (звук чужого процесса как `engine.Source`), `wsclient`, `debpkg`.
  В каталоге место занято под `spotify-go-librespot` и `spotify-librespot` (фаза 9); вместо одной записи `spotify`.
- Шим пишет в unix-сокет движка по протоколу кадров (звук, flush, пауза, громкость) вместо `aplay`; управляющие кадры уходят из потока-писателя, поэтому вызовы
  Soloist не блокируются. Протокол — в шапке `shim/libpulse_shim.c`. Готовый шим (24 КБ, `zig cc`) лежит в git вместе с хэшем и вшивается в бинарник.
- Уступка звука Яндексу и обратно: опрос раз в 250 мс; Яндекс на паузу — новый `mediad.Machine.PauseAll`, Spotify на паузу — команда `pause` по WebSocket.
- Сторож кэша: Soloist сам держит кэш около предела `-z` (за вечер вырос до ≈100 МБ и остановился, на `/data` осталось ≈35 МБ), поэтому компонент при
  `keep_free_mb` (по умолчанию 40 МБ: установка новой версии просит ≥ 28 МБ; было 25, и обновление упёрлось в нехватку места) удаляет самые старые файлы `*.file`.

**Проверено.** Юнит-тесты (go test ./... на Windows и тесты компонента на самой колонке, `GOOS=linux GOARCH=arm64 go test -c`): разбор кадров и поток движка
(пауза с возвратом звука, flush, конец трека, битые привет и кадры), надзор (перезапуск, код 10, зависание, SIGTERM→Kill), WebSocket-клиент и разбор событий Soloist,
сторож кэша, установка (поддельные пакеты, подмена хэша, не-ARM, отказ запуска), ключ, настройки, сквозной тест на поддельном Soloist (процесс-двойник: журнал, WebSocket,
звук в сокет, уступка Яндексу и обратно). На колонке настоящий шим (`shim_test` через загрузчик glibc 2.41) отдал сокету 65 кадров звука, flush, паузу/продолжение
и три кадра громкости (`TestLiveShim`), `/proc` разбирается верно.

**Не проверено (нужна колонка и живой Soloist под управлением компонента).** Установка `openmediad spotify setup` на колонке из сети; звук Spotify через движок
на слух; приглушение под Алису; спектр; наушники; задержка паузы; уступка Яндексу на живой музыке; что удаление файлов кэша не ломает Soloist (по виду это промах кэша);
переживание перезапуска демона и перезагрузки колонки (`cp15_barrier` сбрасывается и выставляется заново).

**Не сделано.** Голос и подборщик (этапы 1–3 плана), компоненты `spotify-go-librespot` и `spotify-librespot`, автоматическое обновление сборки Soloist до срока.

**Обновление 01.11.2026 (после проверки автором на колонке).** Звук, вход, пауза/«дальше» из приложения, перенос в наушники и уступка Яндексу работают.
Найдено и сделано:

- *Громкость.* «Алиса, тише» двигала только колонку, ползунок в Spotify оставался. Теперь громкость одна: Master ↔ ползунок Soloist в обе стороны
  (`volume_sync`, шим громкость не применяет), с защитой от эха и от устаревших данных Soloist.
- *Переименование.* `openmediad spotify rename ИМЯ` или `config set spotify-soloist.device_name`: у демона появился общий хук `Reload(cfg)` для компонентов,
  Soloist перезапускается сам за ≈1 с, демон не перезапускается.
- *Спектр на дисплее не рисуется.* По журналу платформы (`maind.log`): «Spectrum started» для потока Spotify приходит и обновляется каждые 10 с, но
  `device_state_handler` включает слой `[ spectrogram ]` только по `onSDKState` / `onCapabilityStateChanged`, то есть по состоянию плеера, которое задаёт `mediad`.
  Для платформы Spotify не плеер, поэтому кадры принимаются, а анимации нет. Лечится только показом Spotify платформе как плеера (виртуальный плеер:
  события `mediad` с описателем трека, PLAYING/PAUSED; заодно заработают физическая кнопка и «Алиса, пауза»). Описатель плеера сейчас берётся из
  команды платформы (`in.meta.Event`), собственного не строили, поведение платформы на чужое описание неизвестно: это опыт О5 плана, делать с автором у колонки.
- Решение автора: остаёмся на Soloist, librespot и go-librespot пока не подключаем. Дальше — перехват фраз и управление голосом (этапы 1–3 плана).

**Обновление 01.11.2026 (громкость и «Spotify как плеер»).**

- *Громкость, исправление.* Первая версия писала Master в обход платформы, и она «помнила» прежний уровень: ползунок на 30%, потом «тише» давало 90%. Теперь ползунок
  идёт через платформу её собственной командой «громкость N» (текстовый запрос через aliced, `sound_set_level`, без озвучки), а Spotify% = уровень платформы × 5
  (таблица уровней вынесена в `libs/volmap`). Проверено на колонке: «громкость 5» → `Saved volume 10`, `onVolumeChanged … source: voice`, ответ пустой.
- *Spotify как плеер платформы: что выяснено.* Платформа знает только те плееры, которые создала сама (`audio_play` из облака → `AudioCommand` к `mediad`); события чужого плеера
  ей, скорее всего, безразличны, поэтому «виртуальный плеер» одними событиями не сделать. Рабочий путь — «стратегия B» из QUASAR-PROTOCOL.md: **локально попросить платформу
  начать плеер** (без Плюса, без облака) и подставить в него звук Spotify. Точный механизм найден в публичных описаниях протоколов
  (`v3rt3p/quasar-protos`, `yandex_io/protos/remoting.proto`, `yandex_io/sdk/directive_sequencer/protos/directive.proto`): клиент `aliced` шлёт
  `Remoting{remote_object_id=7:"DirectiveSequencer", directive_sequencer_method=23:{method=1:ADD_DIRECTIVES(0), directives=3:[Directive{name=1:"audio_play", request_id=4, json_payload=6:"{…}"}]}}`.
  Тогда платформа сама создаст плеер, пошлёт шиму `prefetch`/`play`, будет слать `pause`/`release` (физическая кнопка, «Алиса, пауза»), включит слой спектра на дисплее и покажет
  метаданные. Что осталось выяснить опытом: JSON `audio_play` (stream, metadata, background_mode), как платформа примет адрес-заглушку, как подставить Spotify в `Back.Open`
  (бэкенд по признаку трека), как вести смену треков и паузу из приложения (новый `audio_play` на каждый трек, события ENDED/PAUSED через автомат).
  Работа отдельным этапом, с автором у колонки.

**Итог опыта с локальным `audio_play` (01.11.2026): не заработало, код отката.** Директива ставилась через aliced по схеме из quasar-protos
(`Remoting{7:"DirectiveSequencer", 23:{1:ADD_DIRECTIVES, 3:[Directive{1:"audio_play", 3:"client_action", 4:uuid, 6:json_payload, 11:1}]}}`).
Платформа **принимает адресата** (в `maind.log` отвечает хост `directive_sequencer_host.cpp`), но на любую форму отвечает
`[error] directive_sequencer_host.cpp:64 Failed to find DirectiveSequencer method in remoting message`. Перебрано: поле метода 1…70 (тело `ADD_LISTENER`),
`ADD_DIRECTIVES` с `directives` (3) и с `directive` (2), поле 23 с пустым телом, `DirectiveHandlerMethod` (поле 2); на объект `DirectiveSequencer_`
платформа молчит. Значит, в этой прошивке хост ждёт метод иначе, чем в публичных protos (они сняты со Станции 2). Директивы по loopback между модулями платформы
не ходят (в записи 10 с трафика `lo` строки `DirectiveSequencer` нет). Игры с `RoutingAudioPlayer`/`AudioPlayer` не помогут: это плееры звука голоса (PLAY_DATA), не музыки.
Снятая с колонки форма настоящей директивы (для будущего): `{"name":"audio_play","type":"client_action","sub_name":"music","payload":{"background_mode":"Ducking",
"metadata":{"title","subtitle","art_image_url","hide_progress_bar","glagol_metadata","switching_streams_metadata"},"stream":{"id","type":"Track","url","alt_urls[3]","decode_key",
"offset_ms","duration_ms","bitrate","codec":"HeAacMp4","format","normalization":{"integrated_loudness","true_peak"}},"callbacks":{on_started,on_finished,on_failed,…},
"scenario_meta":{"@scenario_name":"HollywoodMusic",…},"screen_type":"Music","set_pause":false}}`.

**Перехват фраз, срез 1 (01.11.2026): управление идущей сессией Spotify голосом.** Решение автора после опыта выше. Что сделано:

- `observe.Observer.OnPhrase` отдаёт окончательную фразу (`msg.AliceState.FinalPhrase`, ≈1 с до ответа облака) один раз на запрос; демон передаёт её компонентам с методом
  `InterceptPhrase(reqID, text) bool` (интерфейс `phraseInterceptor`). Первый, кто вернул `true`, забирает фразу.
- `aliced-client.Client.Cancel` отправляет `CancelDialog` (как `c` в `maind --cli`): облако на выполненную фразу не отвечает.
- Шлюз голоса `daemon.voiceGate`: если голос Алисы ведёт компонент движка (`VoiceBackend`), ответ облака на перехваченную фразу гасится (окно 5 с, новая неперехваченная фраза

- Юнит-тесты: таблица (включая 20 «похожих» фраз, которые перехватываться не должны), хозяин звука, настройки, отказ команды, шлюз (прозрачность, одно гашение, срок, снятие),

**Быстрые команды, плеер платформы, лайки, наушники (01.11.2026, проверено автором на колонке).**

- *Быстрые команды* («пауза», «играй», «дальше», «назад» без «Алиса»): платформа узнаёт их командным спотером локально (`command_spotter_capability`, лог maind
  «Command phrase spotted», `fast_command_classifier: Parsed frames=[personal_assistant.scenarios.player.pause]`) и отвечает сама через `local_stack`
  (`fast_command_scenario`) за ≈30 мс. `AliceState BUSY` приходит сразу, поле 2 пустое, текст только в ASR (15.1, 15.2 = 1, 15.4 = 0): `msg.AliceState.FastPhrase`.
  Ответ для «дальше», «назад», «играй» — `audio_play @@mm_stack_engine_get_next` по предсохранённому состоянию очереди Яндекса («local continue»); «пауза» — `clear_queue` +
  анимация, при отсутствии сессии — `player_pause` (`LegacyPlayerDirectiveHandler`).
- *Платформа принимает события плеера, которого сама не запускала* (`AudioClientEvent` без `audio_play`; в её логе только предупреждение «Failed to prase audio context» —
  в дескрипторе нет поля 7), но состояние устройства (`SDKState`, слой `spectrogram` по `onSDKState`) строит по **текущей** сессии `audio_play`. Пока есть сессия Яндекса (даже на паузе),
  события Spotify на дисплей не влияют. Решение: автомат подставляет состояние Spotify под player id сессии платформы (`TakeOver`, `ArmCarrier`, `Machine.vbind`), звук Яндекса при
  этом не играется. Конец трека такому плееру не отправляется (платформа запросила бы у облака следующий трек очереди Яндекса). Перед заменой запуска платформа шлёт «паузу»
  старому плееру: её нужно не передавать Spotify (так «дальше» оставляло трек на паузе).
- *Наушники:* смеситель `bt-out` открывает только 48 кГц, Spotify играл в 44,1 кГц, и `Open` молча падал на динамик. Поток пересчитывается в 48 кГц (`libs/resample`, полифазный фильтр
  Кайзера, ≈2 мс/с на ПК).
- *Web API закрыт по стране (проверено на колонке 01.11.2026):* с адреса в России `api.spotify.com` отвечает 403 «Spotify is unavailable in this country» на любой запрос (`/me`, `/me/library`),
  хотя токен выдаётся (accounts.spotify.com открыт) и Soloist работает. Всё, что идёт через Web API (лайки, поиск «включи <X>», подборщик), требует прокси: настройка `web_proxy`.
  Soloist `play` принимает URI контекстов (плейлист, альбом, исполнитель) без Web API; `spotify:collection:tracks` отвергает («play requires a valid playable Spotify URI»).
- *Лайки:* в Soloist нет команд библиотеки (в бинарнике только очередь, shuffle, repeat), поэтому Web API: `PUT/DELETE /me/library?uris=` (запасной `/me/tracks?ids=`), PKCE, Client ID пользователя,
  токен только на колонке. Вход: `openmediad spotify login`. Подтверждение — короткий сигнал через движок.

Что остаётся (по убыванию разумности):

1. *Подмена при голосовом запросе (Б2/Б3 плана, нужен Плюс).* «Алиса, включи Х» → облако само шлёт `audio_play` Яндекса → автомат перехватывает `prefetch`/`play` и играет вместо него Spotify
   (звук идёт через движок, плеер для платформы настоящий: спектр, кнопка, «пауза»). Это и есть этап «перехват фраз»; без Плюса `audio_play` не приходит.
2. *Glagol (порт 1961, TLS, нужен токен аккаунта Яндекса)*: команды приложению-клиенту, в том числе `externalCommandBypass`; даёт локальный `audio_play` без облака, но требует хранить токен.
3. *Разобрать хост по дизассемблеру `maind`* (`directive_sequencer_host.cpp`, `handleDirectiveHandlerMethod`), чтобы узнать, что он ищет: трудоёмко, результат неочевиден.
4. *Принять, что у сессии из приложения Spotify спектра на дисплее нет* (звук, громкость, пауза, смена трека из приложения, уступка Яндексу работают).
